# 提交工作区

本目录只保存经过源码审阅、真机编译和精度验证后准备上传的唯一候选文件，以及逐次结果记录。

> 路线探索、版本记录、线上提交队列和缓存清理统一遵循 `../文档/统一探索收敛与线上提交流程.md`；各路线的机器可读状态见 `../管理/路线状态/`。

当前本地验证版本为混合方案 `H001-正确性优先/V005`，本机源码使用 `kernel.txt`；同步到服务器和线上模板时才使用 `kernel.asc`。V005 已完成服务器 CANN 编译、链接和三种 dtype 的 NPU 矩阵验证，尚无 CANNJudge 官方分数。调研2（**2026-09-12 重做**）交叉核对：V002 使用**逐字段赋值**配置 DataCopyPad（对字段声明顺序不敏感）；官方字段序本身仍有旧笔记 vs CANN 9.0.0 文档的**证据冲突**，列为真机第一验证项。`GetReduceRepeatSumSpr` 在 9.0.0 有官方专页，主线仍建议 `GetValue(0)+V_S`。

**调研2 对 V002 的三条新增裁决**（详见 `../调研/归档/调研2/Agent10_方案审阅评估与技术报告.md`）：
1. **归一化必须改 `Divs`**：V002 用 `Muls(valueTile, valueTile, invRms)`，主代理 36 组 CPU 复核显示 `Divs` 与 golden 逐位一致（最大绝对差恒为 0），`Muls` 在「大 outer 小 D」下 bf16 最大绝对差达 1.562e-02 并出现真实失配元素。
2. **体量是编译风险**：2955 行 / ~20 个 `Process*` 变体命中官方记载的 `out of jump/jumpc imm range`；首版应收敛为参数化通用路径。
3. **两次 CE 均非算法问题**：V001 为 `pipe_` 符号冲突，V002 为上传内容截断（平台收到首行 `return false;`）。根因是**从未在本地编译成功过一次**。

`V003` 和 `V005` 均归入 `H001-正确性优先`；H002 性能组合的 `MIX-R014-R002-R019-V001` 已完成服务器编译和运行，但大 D FP16 精度未达到提交要求，暂不进入提交队列。V001 的平台失败结果记录在 `混合方案/H001-正确性优先/V001/结果.md`。方案矩阵见 `../调研/归档/调研2/research-report.md` 第 10 章、`../调研/归档/调研2/方案矩阵.md` 与 `../调研/归档/调研2/Agent10_方案审阅评估与技术报告.md`（2026-09-12 版）。

后续版本使用 `V001`、`V002`、`V003` 等三位数字编号，并放入所属方案目录：混合方案使用 `提交/混合方案/H00N-名称/V00N/`，单方案使用 `提交/单方案/R00N-名称/V00N/`。

## 真机生成 V002 候选版本

将候选文件放入平台模板目录后，在模板目录内执行模板提供的 `run.sh`：

```bash
cp /Users/sunyiyang/Desktop/Project/cann/提交/混合方案/H001-正确性优先/V002/kernel.asc \
   /Users/sunyiyang/Downloads/addrmsnormbias_problem_1742_template/kernel.asc
cd /Users/sunyiyang/Downloads/addrmsnormbias_problem_1742_template
source /usr/local/Ascend/ascend-toolkit/set_env.sh
./run.sh
```

上面的安装路径和 `NPU_ARCH` 需要按真机实际环境替换。模板自带用例只有一个 FP16 `[1, 64]` 样例，跑通它只能说明直调入口可运行，不能代表平台 15 个测试点全部通过。
