```text

scalar batch = 8
```

R013：

```text
single buffer
→ double buffer
```

不要在一个版本里同时调五个参数。

# 六、用 Successive Halving，不要每个版本都跑完整大矩阵

这是加快迭代最重要的一点。

### Stage 1：快速淘汰

每个候选：

```text
编译
↓
几个 correctness smoke cases
↓
3~5 个代表性性能 case
↓
每个运行 5~10 次
```

只要：

```text
编译失败
精度失败
性能比 D 慢 >5%
```

直接淘汰。

比如一个 Agent 产生 8 个候选：

```text
8
↓
快速跑
↓
留 4
↓
中等矩阵
↓
留 2
↓
完整矩阵
↓
留 1
```

这就是 Successive Halving。

比：

```text
8 个候选 × 完整矩阵 × 50 次
```

快很多。

# 七、真正的性能比较必须串行

这一点非常重要。

**Codex Agent 可以并行写代码、分析和编译。**

但是：

> 如果只有一张 NPU，多个 Agent 不能同时跑性能测试。

否则：

```text
Agent A kernel
Agent B kernel
系统负载
DVFS
内存带宽争用
```

会把微秒级结果全部污染。

因此架构应该是：

```text
            ┌─ Agent R002 ─ compile ─┐
            ├─ Agent R014 ─ compile ─┤
Orchestrator├─ Agent R015 ─ compile ─┼── Benchmark Queue
            ├─ Agent R028 ─ compile ─┤         │
            └─ Agent R013 ─ compile ─┘         ▼
                                          单独占用 NPU
                                              │
                                              ▼
                                            results
```

即：

### 可以并行

```text
代码生成
静态检查
CPU reference
CANN 编译
日志分析
```

### 必须串行

```text
NPU performance benchmark
```

除非你的服务器有多张相互独立的 NPU。

# 八、不要用“单次最快时间”选择 Champion

本地建议：

```text
warmup = 10
measurement = 30
```

记录：

```text
min
median
p90
```

真正用于排序：

> **median 为主，min 为辅。**

因为：

```text
3.91 μs vs 3.95 μs
```

这种完全可能只是噪声。

建议规定：

```text
< 3%      = 当作无差异
3%~8%     = 可疑，增加重复次数
> 8%      = 值得保留
> 15%     = 明显优化
```

# 九、建立一个统一的 Local Score

不要让 Agent 看见某一个 case 快就说“赢了”。

假设本地有 N 个代表 workload：

\[
S=\exp\left(
\frac1N\sum_i
\log\frac{T_{baseline,i}}{T_{candidate,i}}
\right)
\]

也就是**几何平均加速比**。

简单理解：

```text
S = 1.00   无提升
S = 1.10   整体约快 10%
S = 1.50   整体约快 50%
S = 2.00   整体约 2×
```

同时设置硬约束：

```text
正确性必须 100%
任何核心 workload 不允许退化 >10%
```

这样不会出现：

```text
case 4 快 3×
但其他 10 个 case 慢 40%
```

还被错误选成 Champion。

# 十二、第二阶段采用“贪心前向组合”

假设第一轮最好的是：

```text
R015 = 1.70×
```

那么：

```text
Champion = D + R015
```

接下来再开几个并行 Challenger：

```text
C1 = Champion + R028
C2 = Champion + R014
C3 = Champion + R002
```

测：

```text
C1  2.10×
C2  1.85×
C3  1.62×
```

那么：

```text
Champion = D + R015 + R028
```

下一轮：

```text
Champion + R014
Champion + R002
Champion + R013
```

如此迭代。

这叫：

> **Greedy Forward Selection**

对于你这种 Kernel 优化，非常实用。


这正是你文档里 R029 的作用：根据 `D / outer / UB / core` 做运行时分档。fileciteturn5file0L323-L324

> 找到唯一一个最快 kernel。

> 找到 2~4 个局部最快路径，然后构成一个 dispatcher。

这也是那个参考高性能版本为什么会有：

# 十六、线上结果必须反过来训练“本地筛选规则”

这是非常关键的闭环。

例如：

```text
本地：
Candidate X 比 D 快 30%

线上：
Case 4/6/7 快
Case 14 反而慢
```

那么不能简单说 X 失败。

应该记录：

```text
online behavior
       ↓
推测本地缺少某种 workload family
       ↓
扩充 Full Set
       ↓
重新比较
```

几轮以后，你的本地 benchmark 会越来越接近线上。

最终可能做到：

> Codex 在服务器上自动筛 50~100 个版本，你只需要提交本地前两名。

这就会大幅降低线上实验次数。

## 我建议你现在采用的整体策略

可以概括成一句：

> **并行探索，串行裁决；单因素筛选，贪心组合；局部冠军分档，线上只验证本地冠军。**

第一轮我建议同时让 Codex 启动：

```text
A1 → R002 单遍 y 驻留
A2 → R014 gamma/bias 驻留
A3 → R015 多行 DMA
A4 → R028 标量同步削减
A5 → R013 双缓冲
A6 → R019 reciprocal/Muls
```

每条支线内部自动做小规模参数 sweep，然后统一进入同一个 NPU benchmark queue。

**第一轮只选 Top 3，不做任何组合。**

第二轮再从 Top 3 做：

```text
best
best + second
best + third
```

第三轮继续：

```text
new champion + 下一候选
```

最后才用 R029 把不同 `D/outer` 下的局部冠军组合成一个多路径 kernel。

这会比“按 29 条路线逐个试”快很多，也比“多 Agent 同时随意改一个 kernel”更容易得到真正可解释、可复现的最优版本。

# 1）总目标：怎么最快找到更优方案


| 设计 | 评价 | 建议 |


如果只是同一 NPU 上可以同时跑多个进程，则：

> **不能把同时跑出来的时间拿来做正式性能比较。**

编译和 correctness 可以并行，但 benchmark 应通过设备锁串行。

否则一个优化版本可能只是碰巧运行时其他 Agent 没占带宽。
