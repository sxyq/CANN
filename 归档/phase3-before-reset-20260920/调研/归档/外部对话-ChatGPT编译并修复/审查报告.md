## 3. 技术主线

### 3.1 起点：对两次 Compile Error 的根因判断

助手在 [node 71] 给出的判断（这次是**没有服务器日志**的纯静态推理）：

- `dav-2201`（Atlas A2/A3，含 910B 类）**UB 只有 192 KB**；
- 失败版同时长期驻留 x/residual/xFp32/residualFp32/yFp32/ReduceSum workspace/scalar 七块，怀疑是 **UB 资源布局/固定大 Tile 导致编译阶段资源超限**；
- 参考版按 `rowWidth / dtype / rowCount` 切换 `wideFp32BatchPath_` 等四种布局，本质是在**刻意控制每条路径的 UB footprint**。

这一点与本仓库 `文档/CANNJudge提交自动化调查.md`、V005 结果.md 给出的线上 CE 直接证据（**线上载荷被截断，只剩 118 行，首行从 `AscendC::TBuf` 开始**）**不是同一个原因**。两条轨道对同一现象给出了两种解释，仓库侧的解释有下载文件大小与行数作为物证，对话侧只有静态推理，**尚未互相排除**。

### 3.2 第一个 15/15 Pass 与 A/B/C/D 受控实验

- 首个可用版本：`kTileElems = 2048`→4096，全部 FP32 中间计算，`DataCopyPad` 精确搬运，整行/整 32B 行组分配给单核 [node 137/160]。
- 随后用 A/B/C/D 四个 tile 档位做**受控变量**实验，确认 UB 上限附近仍可编译，并把 **8192 tile + 复用 `residualFp32Buf_`** 的 D 版冻结为全局 baseline [node 214/225/240]。

### 3.3 单变量消融（线上逐个验证）

对话严格执行「一个版本只改一个性能机制」，每条路线都单独上平台取分，再与 D baseline 比几何平均倍数。已测路线：`R002` / `R005` / `R011` / `R013` / `R014` / `R015` / `R019` / `R028` / `R029`，其中 `R014`（gamma/bias 驻留）被确认为强正收益并进入混合。

### 3.4 混合

`MIX-R014-R002-V001` → 15/15 Pass；再叠加 `R019`（标量 `1/rms` + 向量 `Muls`）得到 **`MIX-R014-R002-R019-V001`**，15/15 Pass，成为后续所有实验的统一 Parent。

## 5. 评分公式复核（本次独立验证）

对话早期用了一个自定义公式 `Score = 100/N × Σ min(1, TBest_i / t_i)` 得到 34.19 / 34.80，并在 [node 1029] 自己纠正为「不再用我之前自己复算出来的 34.xx 当作官方分数」，改为直接读平台字段。

本次用该对话提供的两组真实数据独立复核本仓库已经复现的公式 `s_i = 100 / (1 + log₁.₅(t_i / T_i))`，`Score = (Σs_i)/15`：

| 版本 | 复算值（TBest 按对话表格 15 项） | 平台官方值 | 差 |
| --- | ---: | ---: | ---: |
| `R029-V003` | **28.656** | 28.68 | 0.024 |
| `R029-V004` | **28.992** | 29.01 | 0.018 |

结论：

- 本仓库的公式在**两组全新、未经挑选的真实提交**上再次成立（偏差来自平台只显示到 0.1μs / 0.1ms 的舍入）。
- 对话早期的线性公式**是错的**（34.19 / 34.80 vs 28.68 / 29.01），本仓库不应引入该口径。
- `TBest_i` 就是公式里的 `T_i`；对话表格第 3 列起的 15 个数即提交单点用时。

4. **编译失败根因尚未收敛**。仓库侧的「线上载荷截断（118 行）」有物证；对话侧的「UB 资源超限」只是静态推理。两者可能同时成立，也可能只有前者成立。

7. **`R029-V001` / `R029-V002` 无全文**：对话只给了补丁脚本，按脚本原样本机复跑因 needle 不匹配而失败（详见 `提交/外部轨道-ChatGPT编译并修复/MANIFEST.md`）。
8. **该对话的信赖度**：所有分数来自用户回贴的平台截图转文字，本文档未独立访问平台核验；榜行「70 分」也只有用户转述。
