## 二、推荐级别裁决理由

### 首选（S2 / S3 / S7 / S9 / S11 / S13）
- **S13（纯 Ascend C）**：判题仅识别 `kernel.asc` 直调的 `run_kernel` 入口（Agent03§6 / Agent05，A 级），是所有合规提交的形态底线；框架工程（msopgen/`__aicore__` 多文件）无法当作提交物 → **必选形态**。
- **S3（FP32 全中间）**：从根本上消除 fp16 的 `|y|≥256 → Inf` 与 bf16 的相对坍塌（Agent06 Q5/R1，A 级），正确性收益最高、零兼容风险 → **首选精度策略**。
- **S2（单遍暂存）**：将 GM 流量从 7·D·S 降到 5·D·S（−28.6%，Agent07§4，A 级），是性能首选；代价仅是中等的 UB 规划（D≤32768 内可行，B 级）。
- **S7（按行分配）**：标准分核形态，outer≥核数时 48 核满载（Agent07 形态A，A/B）；仅需额外处理 outer<核数的钳制。
- **S9（DataCopyPad 尾块）**：官方 A 级口径称搬出 dummy 自动丢弃（Agent02），且 V002 逐字段赋值天然免疫结构体顺序歧义（§1.1 已定案）→ 首选尾块处理。
- **S11（ReduceSum + GetValue(0)）**：基础 count 版 `ReduceSum` 已足够（§1.7 定案不需要 `GetReduceRepeatSumSpr`），work=1024 经核算足够（§1.4，D 级）；实现简单 → 首选归约方式。

### 可作为第二路线（S1 / S5 / S10 / S12）
- **S1（两遍扫描）**：即 V002 现有结构，算法已正确；代价是 1.4× GM 流量。适合「先保证 15 点全过、暂不做性能」的首版稳妥路线。
- **S5（大 tile）**：减少 ReduceSum+同步次数，受 UB 预算约束；作为性能优化的可选 tile 策略。
- **S10（手工尾块）**：当 S9 的 padding 丢弃行为在真机被证伪（§1.2 / G5）时的兜底，但掩码易错（C 级）。
- **S12（手工向量归约）**：性能上可去标量同步（高潜力），但手写归约顺序差异会引入 1~3 ulp 边界翻转（A 级）+ 掩码易错 → 仅作「去 GetValue」可行性参考，非首选。

### 仅作研究参考（S6 / S14）
- **S6（小 tile）**：同步被放大、性能低，仅用于验证 UB 受限极端形态。
- **S14（GPU 迁移）**：CUDA/Triton 代码无法在 NPU 编译；warp/occupancy/L2 等概念在 Ascend 无对应（Agent04§4-5，C 级逻辑确凿）→ 仅作算法思路借鉴，不可作实现。

### 不建议（S4 / S8）
- **S4（低精度中间）**：fp16 下 `|y|≥256` 直接 Inf 污染整行（A 级），对判题是灾难性失败 → 绝对不建议提交用。
- **S8（按 tile 分配）**：单行跨多核需 WholeReduceSum 跨核归约，大幅复杂化并引入同步/正确性风险（A 级），收益不抵成本 → 不建议。

## 三、本轮明确不推荐的做法

1. **S4 低精度（16-bit 域）中间累加作为提交实现**：`|y|≥256` 时 fp16 平方即 `Inf`，污染整行 → 判题失败（A 级，Agent06 Q5）。仅可作为对照实验。
2. **S8 按 tile 跨核分配**：单行跨核归约（WholeReduceSum 跨 block）使实现复杂度陡增且易错；本题每行独立、无需跨核，收益不抵风险（A 级，Agent03）。
3. **S14 直接移植 GPU/CUDA/Triton 代码为提交物**：无法在 NPU 编译；occupancy/L2/warp-divergence 等 GPU 调优直觉在 Ascend 无对应（Agent04，C 级逻辑确凿）。
4. **把「GPU occupancy / L2 命中 / warp divergence」调优直觉套到本 NPU 题目**：Agent04 已自声明这些概念无 Ascend 对应，套用属无依据（C 级）。
5. **假定 310P/310B 的 UB=256KB 调优结论可直接用于本题**：A2 UB=192KB（B 级，Agent07§2），按 256KB 规划会 UB 超限。
6. **用 `CAST_RND` 枚举（旧别名）**：9.0.0 应为 `CAST_ROUND` / `CAST_RINT`（A 级，Agent02§6）；旧名可能编译不过。
7. **V002 当前 `Muls(y, 1/rms)` 写法保留**：独立复现已确认其会在 bf16 上产生 1~3 ulp 分界翻转（§4 发现3）；应改「先除」`Divs(y, rms)`，零成本消除（与 golden 同链）。
8. **把社区「`dav-2201`=A2 平台要求」当硬约束**：`soc_version:null`，`dav-2201` 仅是模板编译默认（A/⑤，Agent01）；若判题机为 950/A5 需 `dav-3510`，按 A2 编译会指令集不兼容（A 级，Agent08§4）。

## 四、本轮明确无法确认、需真机验证的做法

> 下列结论在资料/静态层面已给出倾向，但**均不能在无 NPU 环境定案**，必须真机首跑验证。

1. **判题 SoC 型号（G1 / P0）**：`soc_version:null`，模板默认 `dav-2201` 非平台约束。影响 `Add/Mul` bf16 支持矩阵、`ReduceSum` 行为、UB 容量（192KB vs 256KB）、向量核数（48 vs 40）、`DataCopyPad` 支持范围。须组委会/提交回传确认。
2. **判题精度判定口径（G2 / P0）**：是否允许少量元素失配、`tol` 取值未知。它直接决定「先除」修正是否必要，以及 bf16 1~3 ulp 是否会判 FAIL。
3. **UB→GM `DataCopyPad` dummy 是否真丢弃（G5 / P0，静默损坏）**：官方 A 级称丢弃，但属静默损坏型风险。需构造 D 非 32B 对齐尾块 + 紧邻有效数据，搬出后读相邻内存是否被改写。
4. **`ReduceSum` 官方 `workLocal` 尺寸公式（G3 / B）**：按社区公式 `WORK_LEN=1024` 足够（count=4096→512<1024），但官方无显式公式；fp16/bf16 大 tile 建议真机验 A2 上 D=4096 单块 `ReduceSum(count=4096, fp32)`。
5. **`CAST_RINT` 是否 = RNE 舍入（G4 / P1）**：影响 bf16 末级舍入方向，需真机构造量化分界样本核对。
6. **15 测试点具体 shape/dtype/epsilon（G6 / B1）**：平台未公开（`visible=0`），测试矩阵只能按边界枚举推测，须提交后反推。
7. **`sqrtf` 在 NPU 的指令映射 / fast-math 改写（G7 / R3）**：标量 sqrt 精度与 fast-math 改写行为须真机确认；若被改写为低精度倒数，即便 S3 也难保 bf16 判定。
8. **S9「dummy 丢弃」成立前提下 S2 单遍暂存的 UB 可行性**：D=32768 fp32 整行 128KB + 5 队列在 192KB UB 下是否安全、双缓冲（BUFFER_NUM=2）能否容纳，需在真机 `InitBuffer` 阶段实测。
9. **V002「改名修复编译」是否成立（§1.3）**：V002 平台失败已确诊为上传内容截断（首行 `return false;`），405 行代码**从未真正编译过**；须全选替换为本地完整 405 行重新提交，观察是否进入运行期。若仍 `Compile Error` 才是真正的代码编译问题。
