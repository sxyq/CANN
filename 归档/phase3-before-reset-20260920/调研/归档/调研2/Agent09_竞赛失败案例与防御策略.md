## 1. 竞赛六大致命失败形态（Failure Modes）全景复盘

算子竞赛中最容易导致成绩清零的六类核心故障形态如下：

```text
               ┌── 1. Compile Error (CE)  --> 头文件冲突、编译器宏冲突、函数修饰符不符
               ├── 2. Wrong Answer (WA)   --> 尾块越界踩踏、归约临时区不足、截断舍入偏差
算子竞赛致命故障 ├── 3. Runtime Error (RE)  --> 片上 UB 溢出、TQue 资源死锁、空指针解引用
               ├── 4. Timeout (TLE)       --> 标量反复等待、Stream 3000ms 超时挂起
               ├── 5. Format Error (FE)   --> 提交物结构错误、遗留本地绝对路径
               └── 6. Quota Exhaustion    --> 盲目试错耗尽每日 50 次提交配额
```

## 2. 真实踩坑案例与底层机理剖析

### 2.1 案例一：尾块写回导致相邻行被无情踩踏（Wrong Answer） **[高危]**
- **现象**：在小规模测试点或 $D$ 为 32 整数倍时全部通过；一旦遇到 $D=67, 129, 1000$ 等非 32 对齐用例，第二行及后续行精度全线崩溃（最大误差达 $100\%$）。
- **根因分析**：
  在全局内存（GM）中，张量是行优先连续紧凑排列的，第 $r$ 行的末尾与第 $r+1$ 行的起始地址紧挨着。  
  如果开发者使用 `DataCopyPad` 搬出尾块时，底层 DMA 若按照 32 字节 Burst 粒度强制写回，且未在硬件层面进行字节掩码丢弃，则尾块最后的 Padding 脏数据（例如填补的 0 或旧值）就会覆盖写到第 $r+1$ 行的第一个数字！
- **防御对策**：
  1. 使用严格的 `DataCopyExtParams` 指定精确到字节的 `blockLen = valid_len * sizeof(T)`；
  2. 在本地 CPU 模拟与真机回归阶段，专门注入非 32 对齐张量（如 $D=67$），检查输出连续内存中行与行之间的边界字节。

### 2.2 案例二：`ReduceSum` 临时缓冲区过小引发诡异精度丢失（Wrong Answer） **[高危]**
- **现象**：算子在本地编译成功，小数据量精度通过，但当 $D \ge 1024$ 时归约和计算结果出现偶发性漂移，甚至变为 NaN。
- **根因分析**：
  `ReduceSum` 矢量指令在执行多步树状累加时，极度依赖 `workLocal` 临时空间。如果分配给 `workLocal` 的大小低于公式：
  $$\text{workLen} < \text{RoundUp}(\text{count} / 64, 8) \times 8$$
  指令会悄悄写出界，破坏 UB 中紧邻的其他缓冲区（如 `value_float_` 或输入队列），导致无法定位的静默内存踩踏。
- **防御对策**：
  在 `TPipe` 初始化时，为 `work_` 强行分配 $1024$ 个 float（4KB），支持最大 8192 个元素的归约工作区，从物理上杜绝缓冲区溢出。

### 2.3 案例三：UB 申请超限引发内核静默死机（Runtime Error） **[极高危]**
- **现象**：提交到判题机后，报 `Runtime Error` 或直接引发系统段错误（Segmentation Fault）。
- **根因分析**：
  部分开发者为了提升并发度，盲目将 `BUFFER_NUM` 设为 4，或为每个变量都分配 $32768$ 长度的局部张量。总 UB 请求量高达 $500\text{KB}$，远超 Atlas A2 的 $192\text{KB}$ 物理限制。`tpipe.InitBuffer` 失败返回空指针，后续 `AllocTensor` 触发非法内存访问。
- **防御对策**：
  严格按 108 KB 的安全峰值预算规划 UB（见 Agent 7 报告），绝不动态申请不可控的超大内存。

### 2.4 案例四：`GetValue` 滥用引发流水线死锁与 Stream 超时（Timeout） **[中危]**
- **现象**：判题系统在执行第 10 秒抛出 `aclrtSynchronizeStreamWithTimeout failed, ret=507000`（超时）。
- **根因分析**：
  在每处理一个 Tile 甚至每计算几个元素就调用一次 `GetValue(0)`。因为 Vector 单元与 Scalar 单元速度不匹配，每一次 `GetValue` 都强制触发硬件握手，指令发射队列长期排空，导致 5 次迭代执行耗时超过 3000ms 的判题超时硬门限。
- **防御对策**：
  整行只在完成所有 Tile 的累加后触发一次标量结算；后续性能优化版本优先切向 `GetReduceRepeatSumSpr`。

## 3. 十大自查与防爆检查清单（Pre-Flight Checklist）

在每一次生成候选版本（如 V002 / V003）并准备真机编译验证前，必须严格执行以下检查：

```markdown
- [ ] 1. 【命名安全】类成员严禁使用 `pipe_`，统一采用 `TPipe tpipe;`。
- [ ] 2. 【入口对齐】核函数限定符逐字核对为 `__global__ __vector__`。
- [ ] 3. 【无凭据泄露】源码全局搜索 `token|password|secret|key`，结果为空。
- [ ] 4. 【禁止代算】核函数内部包含完整的相加、平方、归约、开方、归一化与仿射指令，严禁 Host 代算。
- [ ] 5. 【UB 峰值】核对 `tpipe.InitBuffer` 总字节数，严格低于 160KB 安全线。
- [ ] 6. 【单次归约上限】`ReduceSum` 的入参 `count` 严格受控在 $\le 4096$。
- [ ] 7. 【workLocal 容量】`workLocal` 分配空间严格 $\ge 1024$ 个 float。
- [ ] 8. 【舍入模式】半精度转单精度使用 `CAST_NONE`，单精度转半精度使用 `CAST_RINT`。
- [ ] 9. 【尾块隔离】非 32 对齐时使用 `DataCopyPad` 并指定准确的字节长度，严禁踩踏相邻行。
- [ ] 10.【无绝对路径】提交的 `kernel.asc` 内部不包含任何本地开发机的绝对文件路径。
```
