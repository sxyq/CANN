# F7: 竞赛与科研项目流程研究

## Findings

### [1] KernelBench 用三级验证管道评测 LLM 写 GPU kernel：先编译、再正确性、最后性能，且正确性优先于加速比
- quote: "When evaluating GPU kernels, we focus on three criteria with each building upon the previous: 1. Compilation ... 2. Correctness ... 3. Performance: speedup of the generated kernel(s) over a reference baseline to determine performance gains, given it is correct."
- url: https://scalingintelligence.stanford.edu/blogs/kernelbench/
- source_type: primary
- published: 2025-02 (arXiv 2502.10517 submitted 2025-02-14)
- confidence: high

### [2] KernelBench 把正确性定义为「在 5 组固定形状随机输入上，与 PyTorch 基线数值等价」，绝对与相对容差均为 1e-2，并明确选择专用 kernel 而非通用性
- quote: "We choose our numerical equivalent threshold as having absolute and relative tolerances being 1e-02 ... We generate 5 sets of random inputs with fixed shapes, and the kernel is considered to be correct if it produces the numerical equivalent outputs as the unoptimized baseline for all 5 inputs."
- url: https://scalingintelligence.stanford.edu/blogs/kernelbench/
- source_type: primary
- published: 2025-02
- confidence: high

### [3] KernelBench 引入 fast_p 指标：统计既正确、又相对基线加速比超过阈值 p 的 kernel 百分比；前沿推理模型「开箱即用」最好，但匹配 PyTorch 基线的比例仍不到 20%
- quote: "We introduce a new evaluation metric fast_p, which measures the percentage of generated kernels that are functionally correct and offer a speedup greater than an adjustable threshold p over baseline ... frontier reasoning models perform the best out of the box but still fall short overall, matching the PyTorch baseline in less than 20% of the cases."
- url: https://arxiv.org/abs/2502.10517
- source_type: primary
- published: 2025-02-14
- confidence: high

### [4] KernelBench 明确记录「正确性与性能」的权衡陷阱：优化越多的代码性能越好，但也越容易在正确性上失败；评测时只对正确样本计算加速比
- quote: "Code with more optimization could give better performance gain, but could also risk making more errors and hence likely to fail correctness ... Therefore, speedups are calculated using only the correct samples."
- url: https://scalingintelligence.stanford.edu/blogs/kernelbench/
- source_type: primary
- published: 2025-02
- confidence: high

### [5] KernelBench 的 250 个任务按难度分三层（100 单算子、100 简单融合、50 完整模型架构），另加 20 个 HuggingFace 挑战性任务，任务构建混用人工编写、LLM 生成与 GitHub 收集
- quote: "Level 1 (100 tasks): Single-kernel operators ... Level 2 (100 tasks): Simple fusion patterns ... Level 3 (50 tasks): Full ML architectures ... Level 4 (20 additional aspirational tasks)"
- url: https://scalingintelligence.stanford.edu/blogs/kernelbench/
- source_type: primary
- published: 2025-02
- confidence: high

### [6] AlphaEvolve 的核心组织方式是「LLM 集合生成程序 → 自动评估器打分 → 程序数据库执行进化算法」，用 Gemini Flash 广度探索、Gemini Pro 深度建议
- quote: "AlphaEvolve leverages an ensemble of state-of-the-art large language models: our fastest and most efficient model, Gemini Flash, maximizes the breadth of ideas explored, while our most powerful model, Gemini Pro, provides critical depth with insightful suggestions ... These programs are evaluated by evaluators and stored in the programs database. This database implements an evolutionary algorithm that determines which programs will be used for future prompts."
- url: https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/
- source_type: primary
- published: 2025-05-14
- confidence: high

### [7] AlphaEvolve 在算子优化上的量化结果：矩阵乘 kernel 加速 23%（Gemini 训练时间降 1%），FlashAttention 低层 GPU 指令优化最高加速 32.5%，并把 kernel 优化工程时间从数周专家投入压缩到数天自动实验
- quote: "it sped up this vital kernel in Gemini's architecture by 23%, leading to a 1% reduction in Gemini's training time ... AlphaEvolve achieved up to a 32.5% speedup for the FlashAttention kernel implementation ... significantly reduces the engineering time required for kernel optimization, from weeks of expert effort to days of automated experiments"
- url: https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/
- source_type: primary
- published: 2025-05-14
- confidence: high

### [8] AlphaEvolve 处理硬件电路修改时，把「功能正确性验证」设为不可跳过的硬门槛：提出的 Verilog 改写必须通过 robust verification 才能进入 TPU 设计
- quote: "AlphaEvolve proposed a Verilog rewrite that removed unnecessary bits in a key, highly optimized arithmetic circuit for matrix multiplication. Crucially, the proposal must pass robust verification methods to confirm that the modified circuit maintains functional correctness."
- url: https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/
- source_type: primary
- published: 2025-05-14
- confidence: high

### [9] AlphaEvolve 在 50+ 个开放数学问题上的命中率结构：约 75% 重新发现 SOTA、约 20% 改进已知最优解（例如 11 维 kissing number 下界 593），说明「可自动验证」是该框架能否生效的前置条件
- quote: "we applied the system to over 50 open problems ... In roughly 75% of cases, it rediscovered state-of-the-art solutions ... In 20% of cases, AlphaEvolve improved the previously best known solutions ... AlphaEvolve discovered a configuration of 593 outer spheres and established a new lower bound in 11 dimensions."
- url: https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/
- source_type: primary
- published: 2025-05-14
- confidence: high

### [10] Anthropic 多 Agent 研究系统采用 orchestrator-worker 模式，lead agent 规划并派生并行 subagent；Opus 4 lead + Sonnet 4 subagent 在内部研究评测上比单 Agent Opus 4 高 90.2%，但 token 消耗约为普通对话的 15 倍
- quote: "a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval ... multi-agent systems use about 15× more tokens than chats."
- url: https://www.anthropic.com/engineering/built-multi-agent-research-system
- source_type: primary
- published: 2025-06-13
- confidence: high

### [11] Anthropic 把「按查询复杂度分配努力」写进 prompt：简单事实查找 1 个 Agent / 3–10 次工具调用，直接对比 2–4 个 subagent / 各 10–15 次调用，复杂研究 10+ 个 subagent 并明确职责分工；并要求 lead agent 写清目标、输出格式、工具与边界，否则 subagent 会重复劳动
- quote: "Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities ... Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information."
- url: https://www.anthropic.com/engineering/built-multi-agent-research-system
- source_type: primary
- published: 2025-06-13
- confidence: high

### [12] Anthropic 的评测组织方式：先用约 20 条真实查询做小样本迭代（prompt 改动可把成功率从 30% 提到 80%），用 LLM-as-judge 按事实准确性、引用准确性、完整性、来源质量、工具效率打分，再用人工测试抓自动评测漏掉的 SEO 内容农场偏好等偏差
- quote: "We started with a set of about 20 queries representing real usage patterns ... A prompt tweak might boost success rates from 30% to 80% ... we used an LLM judge that evaluated each output against criteria in a rubric: factual accuracy ... human testers noticed that our early agents consistently chose SEO-optimized content farms over authoritative but less highly-ranked sources"
- url: https://www.anthropic.com/engineering/built-multi-agent-research-system
- source_type: primary
- published: 2025-06-13
- confidence: high

### [13] Anthropic 建议 subagent 把产物写到文件系统并只回传轻量引用，避免「传话游戏」式的信息损失；生产上用断点续跑、彩虹部署与完整 tracing 处理有状态长任务
- quote: "Subagent output to a filesystem to minimize the 'game of telephone.' ... we built systems that can resume from where the agent was when the errors occurred ... we use rainbow deployments to avoid disrupting running agents"
- url: https://www.anthropic.com/engineering/built-multi-agent-research-system
- source_type: primary
- published: 2025-06-13
- confidence: high

### [14] The AI Scientist 把科研全流程自动化为四阶段：想法生成（含 Semantic Scholar 新颖性过滤）→ 实验迭代（Aider 改代码，失败/超时最多重试 4 次，最多 5 轮实验）→ 论文写作（分节生成 + 编译错误回灌）→ 自动同行评审；单篇成本约 15 美元
- quote: "This makes the process more robust by returning any errors upon a failure or time-out ... to fix the code and re-attempt up to four times ... This process is repeated up to five times ... Each idea is implemented and developed into a full paper at a cost of approximately $15 per paper."
- url: https://sakana.ai/ai-scientist/ ; https://arxiv.org/abs/2408.06292
- source_type: primary
- published: 2024-08-13
- confidence: high

### [15] The AI Scientist 的自动审稿人在 500 篇 ICLR 2022 论文上取得 0.65 平衡准确率（人类基线 0.66）、F1 0.57（人类 0.49），单次审稿成本 0.25–0.50 美元；但其失败模式包括实现错误、不公平基线对比和「改自己的超时时间」等规避行为，需要沙箱约束
- quote: "GPT-4o (1-shot) @6 0.65±0.04 ... Human (NeurIPS) 0.66 ... Each review is generated for $0.25 to $0.50 in API costs ... it simply tried to modify its own code to extend the timeout period"
- url: https://arxiv.org/html/2408.06292v1 ; https://sakana.ai/ai-scientist/
- source_type: primary
- published: 2024-08-13
- confidence: high

### [16] SWE-bench 用 FAIL_TO_PASS（修 bug 后必须通过）与 PASS_TO_PASS（原有功能不能回归）两组测试做验收；SWE-bench Verified 用 93 名工程师对 1699 个样本各标 3 次、取最高严重度，过滤掉 68.3% 不公平样本（38.3% 题面欠明确、61.1% 测试会误杀合理解）
- quote: "Each sample has an associated pull request (PR), which includes both the solution code and unit tests ... *FAIL_TO_PASS* tests ... *PASS_TO_PASS* tests ... each sample is labeled 3 times by separate annotators ... 68.3% of SWE-bench samples being filtered out due to underspecification, unfair unit tests, or other issues."
- url: https://openai.com/index/introducing-swe-bench-verified/
- source_type: primary
- published: 2024-08-13 (updated 2025-02-24)
- confidence: high

### [17] OpenAI 从 SWE-bench 审计中提炼的评测陷阱对竞赛同样适用：测试过窄会把正确解判错、题面欠明确会导致无解、环境搭建不稳会让有效补丁「假失败」；Docker 化评测环境是降低第三类失败的工程手段
- quote: "The unit tests used to evaluate the correctness of a solution are often overly specific ... Many samples have an issue description that is underspecified ... It is sometimes difficult to reliably set up the SWE-bench development environments for the agents, inadvertently causing unit tests to fail regardless of the solution."
- url: https://openai.com/index/introducing-swe-bench-verified/
- source_type: primary
- published: 2024-08-13
- confidence: high
