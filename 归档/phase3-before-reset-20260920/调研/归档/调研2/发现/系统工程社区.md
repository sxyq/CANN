# F4: Linux与系统工程社区

## Findings

### [1] Linux 内核采用约 2 周 merge window + 6–10 周稳定期的滚动发布；单次发布约 13,000 changesets，merge window 期间峰值接近每天 1,000 个 changesets；是否收尾的首要指标是历史版本回归列表，而非新功能数量。
- quote: "A typical release can contain about 13,000 changesets with changes to several hundred thousand lines of code. ... the bulk of changes for a new development cycle (and all of the major changes) will be merged during this time, at a rate approaching 1,000 changes per day. ... The most significant metric used is the list of regressions from previous releases."
- url: https://www.kernel.org/doc/html/latest/process/2.Process.html
- source_type: primary
- published: unknown (Linux 7.3.0-rc2 docs snapshot, accessed 2026-09-11)
- confidence: high

### [2] 内核补丁的正式生命周期被拆成 Design → Early review（邮件列表）→ Wider review（子系统维护者 + linux-next）→ mainline merge → stable → long-term maintenance 六步；官方文档明确指出把流程压缩成“一步合入”是开发者/雇主最大的错误。
- quote: "The stages that a patch goes through are, generally: Design. ... Early review. ... Wider review. ... Merging into the mainline. ... Stable release. ... Long-term maintenance. ... One of the largest mistakes made by kernel developers (or their employers) is to try to cut the process down to a single \"merging into the mainline\" step."
- url: https://www.kernel.org/doc/html/latest/process/2.Process.html
- source_type: primary
- published: unknown (accessed 2026-09-11)
- confidence: high

### [3] 内核用“中尉 + 信任链”子系统维护者树做任务拆分与合入：2.6.38 的 9,500+ 个补丁中只有约 112 个（~1.3%）由 Linus 直接挑选；补丁须先找到正确子系统维护者与邮件列表，而不是直发 Linus。
- quote: "of the over 9,500 patches which went into the 2.6.38 kernel, only 112 (around 1.3%) were directly chosen by Linus himself. ... this process is known as the \"chain of trust.\" ... Sending patches directly to Linus is not normally the right way to go."
- url: https://www.kernel.org/doc/html/latest/process/2.Process.html
- source_type: primary
- published: unknown (accessed 2026-09-11)
- confidence: high

### [4] 官方补丁提交规范要求：每个逻辑变更拆成独立 patch；patch series 中间任一点都必须能编译运行（为 git bisect 服务）；性能类改动必须附上量化数字和代价权衡，而非只写“更快”。
- quote: "Separate each logical change into a separate patch. ... take special care to ensure that the kernel builds and runs properly after each patch in the series. ... Quantify optimizations and trade-offs. If you claim improvements in performance, memory consumption, stack footprint, or binary size, include numbers that back them up."
- url: https://www.kernel.org/doc/html/latest/process/submitting-patches.html
- source_type: primary
- published: unknown (accessed 2026-09-11)
- confidence: high

### [5] linux-next 是 merge window 之前跨子系统集成测试的强制通道：进入下一 merge window 的所有补丁“应该”在窗口打开前先进入 linux-next；另有 -mm 树作为“最后手段”的子系统树（约 5–10% 主线补丁经其进入）。
- quote: "Linux-next has become an integral part of the kernel development process; all patches merged during a given merge window should really have found their way into linux-next some time before the merge window opens. ... In a typical development cycle, approximately 5-10% of the patches going into the mainline get there via -mm."
- url: https://www.kernel.org/doc/html/latest/process/2.Process.html
- source_type: primary
- published: unknown (accessed 2026-09-11)
- confidence: high

### [6] 内核测试被正式分成两层：KUnit（内核内白盒单测，针对小而独立的代码路径，构建/运行极快）与 kselftest（用户态系统/端到端测试，测 syscall/设备/文件系统等用户可见接口）；输出必须符合 TAP 以便 CI 解析；默认单测超时 45 秒。
- quote: "KUnit is an entirely in-kernel system for \"white box\" testing ... best written against small, self-contained parts of the kernel. ... kselftest ... is largely implemented in userspace ... aligned well with 'system' or 'end-to-end' testing. ... The output of tests must conform to the TAP standard ... CI systems can easily parse TAP output. ... a default timeout is used of 45 seconds for each test."
- url: https://www.kernel.org/doc/html/latest/dev-tools/testing-overview.html
- source_type: primary
- published: unknown (accessed 2026-09-11)
- confidence: high

### [7] kselftest 设计为可跨版本回归：主线测试套件被跑在旧 stable 内核上；新增测试若针对既有 bug 做回归，应能在旧内核上优雅 skip；CI 可用 FORCE_TARGETS=1 强制所有 target 必须构建成功，避免静默部分失败。
- quote: "Kselftest from mainline can be run on older stable kernels. ... when a new test gets added to test existing code to regression test a bug, we should be able to run that test on an older kernel. ... Set FORCE_TARGETS=1 to instead require every target to build successfully ... useful in CI environments where a silent partial build would be misleading."
- url: https://www.kernel.org/doc/html/latest/dev-tools/kselftest.html
- source_type: primary
- published: unknown (accessed 2026-09-11)
- confidence: high

### [8] 2005 年 LWN 记录的自动化内核回归矩阵（Martin Bligh 的 abat）：在发布后约 15 分钟内自动构建并启动 mainline / -mjb / -mm 内核，在异构机器矩阵（4×AMD64、16×NUMA-Q、4×NUMA-Q、32×x440 ia32、PPC64 Power5 LPAR、PPC64 Power4 LPAR/裸机）上跑 dbench/tbench/kernbench/reaim/fsx；kernbench 性能图直接暴露 -mm 相对 mainline 的性能下滑，并定位到当时 -mm 中的 36 个调度器补丁。
- quote: "Currently it builds and boots any mainline, -mjb, -mm kernel within about 15 minutes of release. runs dbench, tbench, kernbench, reaim and fsx. Currently I'm using a 4x AMD64 box, a 16x NUMA-Q, 4x NUMA-Q, 32x x440 (ia32) PPC64 Power 5 LPAR, PPC64 Power 4 LPAR, and PPC64 Power 4 bare metal system. ... The -mm trees, however, perform notably worse than the mainline ... the current suspect is the (36!) scheduler patches currently living in -mm."
- url: https://lwn.net/Articles/139123/
- source_type: secondary
- published: 2005-06-08
- confidence: high

### [9] MMTests（Mel Gorman，至少自 2012 年起）是内核性能测量的标准框架：用 Bash+Perl 完成 benchmark 的获取/构建/配置/运行，保存配置与结果，用 compare_mmtests.pl 做 run-to-run 对比，用 graph-mmtests.sh 出图，monitor 功能可采集 top/vmstat/iostat/ftrace/perf；显著性判断虽内置但输出提示极不明显、且几乎无文档——这是真实工程中“有统计但被忽略”的失败模式。
- quote: "The MMTests suite dates back to at least 2012 ... mostly implemented in a combination of Bash and Perl. The core suite is able to fetch, build, configure, and run a whole range of benchmarks. Multiple runs can be made, with MMTests collecting and storing both the configuration that was used and the results ... there is absolutely none [documentation]. ... MMTests does enough evaluation to try to guess whether a specific difference is significant; that is rather subtly marked in the output and is often missed."
- url: https://lwn.net/Articles/820823/
- source_type: secondary
- published: 2020-05-19
- confidence: high

### [10] 虚拟化场景下的性能对比必须做主机/客户机同步屏障：SUSE 的 Dario Faggioli 在 MMTests 上扩展了 host-guest token 屏障——每个 benchmark 前 host 等所有 guest ready 再同时放行；否则同一组测试在不同 VM 里时间轴错位，结果不可重复、不可比较。这是“设备/环境差异导致测量失真”的典型案例与解决过程。
- quote: "The only way to get clear and deterministic results is to ensure that the benchmark runs on all systems run in a synchronized manner. ... Synchronization ... is handled by passing tokens between the host and the virtual machines; the guests never talk directly to each other. The host implements a \"barrier\" before each benchmark run; once every virtual machine has informed the host that it is ready for the next test, they are all told to proceed."
- url: https://lwn.net/Articles/820823/
- source_type: secondary
- published: 2020-05-19
- confidence: high

### [11] Ansor（OSDI 2020）把 GPU/CPU Kernel 调优流程化为“分层搜索空间采样 + 进化搜索 + 学习成本模型 + 任务调度器并行优化多个子图”，并明确指出失败原因：vendor kernel 库需要大量平台特化工程，而已有搜索策略因搜索空间受限和探索策略无效而找不到高性能程序；在 Intel CPU/ARM CPU/NVIDIA GPU 上相对当时 SOTA 最高提升 3.8×/2.6×/1.7×。
- quote: "these approaches either require significant engineering effort to develop platform-specific optimization code or fall short of finding high-performance programs due to restricted search space and ineffective exploration strategy. ... Ansor utilizes a task scheduler to simultaneously optimize multiple subgraphs in deep neural networks. We show that Ansor improves the execution performance ... on the Intel CPU, ARM CPU, and NVIDIA GPU by up to 3.8×, 2.6×, and 1.7×, respectively."
- url: https://arxiv.org/abs/2006.06762
- source_type: primary
- published: 2020-06-11 (OSDI 2020)
- confidence: high

### [12] Triton-Ascend（昇腾官方 Triton 后端）的 autotune 工程约定：`configs=[]` 表示由 Ascend backend 按 kernel DSL 与运行时 shape 自动生成 Tiling 候选，生成时会按 NPU 片上存储容量、对齐约束、核数利用率做筛选而非盲目枚举；默认并行编译候选配置；`TRITON_BENCH_METHOD='npu'` 可切到 profiler 只测片上计算时间（对短 kernel 更准）。官方同时承认自动 Tiling 做了大量剪枝，“不保证达到手工极致调优上限”，失败时必须回退手写 `triton.Config`。
- quote: "configs=[] 在 Triton-Ascend 中表示\"由 Ascend backend 自动生成候选配置并完成寻优\" ... Ascend backend 在生成候选时，会结合 NPU 的片上存储容量、对齐约束、核数利用等边界做筛选，而不是单纯枚举一批配置再盲目 benchmark。 ... 当前自动 Tiling 会对生成配置数量做大量剪枝，因此并不保证自动生成结果一定能达到手工极致调优的性能上限。 ... 如果自动 Tiling 模式无法生成任何可用候选配置，这时需要用户改为手写 triton.Config。"
- url: https://triton-ascend.readthedocs.io/zh-cn/latest/autotune_guide.html
- source_type: primary
- published: unknown (accessed 2026-09-11)
- confidence: high

### [13] Triton-Ascend autotune 的可操作约束（版本兼容/设备差异相关）：必须先 `import triton.backends.ascend.runtime` 才进入 Ascend 扩展路径，否则仍走社区 autotune 且 `configs=[]` 不会触发自动 Tiling；`@triton.autotune` 必须直接包在 `@triton.jit` 外层；希望参与自动调优的 `tl.constexpr` 不能在 launch 时写死、也不能在 kernel 定义中给默认值；影响 grid 的 Tiling 参数必须把 grid 写成 `lambda meta` 形式。
- quote: "只有导入下面这行后，才会进入 Triton-Ascend 的 autotune 扩展路径：import triton.backends.ascend.runtime ... @triton.autotune 必须直接包在 @triton.jit 外层 ... 如果你在 launch 时显式传入 BLOCK_M=128，那这个参数就已经被固定，不再属于自动生成范围。 ... grid 必须写成依赖 meta 参数的 lambda 形式。"
- url: https://triton-ascend.readthedocs.io/zh-cn/latest/autotune_guide.html
- source_type: primary
- published: unknown (accessed 2026-09-11)
- confidence: high

### [14] 闭门开发在大型内核工程中系统性失败：官方早期规划文档点名三个真实案例——Devicescape 网络栈为单处理器设计，被迫事后补锁导致（后改名 mac80211）合入延迟超过一年；Reiser4 因把本应下沉到 VFS 的能力做进文件系统、且存在用户可触发死锁而始终未进主线；AppArmor 因不安全使用 VFS 内部结构被挡在主线外多年。结论是先定义问题、再与社区早期讨论，而不是先写完再投。
- quote: "kernel code which is designed and developed behind closed doors invariably has problems which are only revealed when the code is released into the community. ... The Devicescape network stack ... could not be merged into the mainline until it was made suitable for multiprocessor systems ... the merging of this code (now called mac80211) was delayed for over a year. ... Reiser4 ... has caused Reiser4 to stay out of the mainline kernel. ... AppArmor ... kept AppArmor out of the mainline for years."
- url: https://www.kernel.org/doc/html/latest/process/3.Early-stage.html
- source_type: primary
- published: unknown (accessed 2026-09-11)
- confidence: high

### [15] 2026 年 LSFMM+BPF 峰会上 BPF 维护者 Alexei Starovoitov 对 LLM/Agent 写内核补丁的一线反馈：coding agent 需要紧反馈环，而 BPF 的 verifier 错误“疯狂”、是其观察到的唯一会让 LLM 直接放弃而非硬产出的场景；目标是让通过 Rust 编译器的普通 BPF 程序也能通过 verifier，并把错误信息改成 Rust 风格的“发生了什么 + 怎么修”。同时 BPF 子系统被低质量 LLM 补丁淹没，维护者已默认不信 commit log、只看 diff，并公开表示“maintainers don't scale”、要求提交者也参与 review。这是 Linux 社区对多 Agent 并行产出最直接的一手工程反馈。
- quote: "Coding agents do their best work when given tight feedback loops ... errors from the verifier \"are insane\" — huge dumps of data that obscure the actual source of the problem. In Starovoitov's experience, writing BPF code is the only case he has observed where LLMs will give up rather than producing something. ... The BPF subsystem is swamped with low-quality patches that look, on first impression, really good. At this point, he is ignoring the commit log on the assumption that it is written by LLMs and just looking directly at the patches themselves. But, in general, \"maintainers don't scale\"."
- url: https://lwn.net/Articles/1075067/
- source_type: secondary
- published: 2026-06-03
- confidence: high

### [16] vLLM-Ascend 采用“硬件可插拔”社区插件模式接入昇腾 NPU（遵循 vLLM RFC Hardware pluggable），把 NPU 集成与 vLLM 核心解耦；其文档体系单独分出 Evaluation 与 Performance and Debug 两块，说明昇腾上的算子/推理性能工作被当作独立可回归的工程面，而不是一次性调参。
- quote: "vLLM Ascend plugin (vllm-ascend) is a community-maintained hardware plugin for running vLLM on the Ascend NPU. ... It adheres to the principles outlined in the [RFC]: Hardware pluggable, providing a hardware-pluggable interface that decouples the integration of the Ascend NPU with vLLM."
- url: https://docs.vllm.ai/projects/ascend/en/latest/
- source_type: primary
- published: unknown (latest developer preview docs, accessed 2026-09-11)
- confidence: medium

### [17] 内核静态/动态分析工具链被正式分层并说明了各自失败模式：Sparse（类型/锁/值域检查）、Smatch（跨函数流分析、缓冲区大小/索引可控性）、Coccinelle（宏展开前检查、可自动生成补丁）；官方明确警告静态分析有 false positive，必须人工评估后再修，且 Smatch 与 Coccinelle 的能力边界不同（Coccinelle 不做值分析）。配套动态工具包括 KASAN/KMSAN/KCSAN/KFENCE/kmemleak/lockdep，可与 KUnit/kselftest 组合以在测试期间捕捉错误类问题。
- quote: "Beware, though, that static analysis tools suffer from false positives. Errors and warns need to be evaluated carefully before attempting to fix them. ... Coccinelle does no analysis of variable values, which is the strong point of Smatch. ... These tools [dynamic] tend to test the kernel as a whole, and do not \"pass\" like kselftest or KUnit tests. They can be combined with KUnit or kselftest by running tests on a kernel with these tools enabled."
- url: https://www.kernel.org/doc/html/latest/dev-tools/testing-overview.html
- source_type: primary
- published: unknown (accessed 2026-09-11)
- confidence: high
