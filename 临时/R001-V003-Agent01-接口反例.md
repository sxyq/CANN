# R001/V003 Agent-1：接口与反例复核

## 结论

- 当前仓库没有 `提交/混合方案/H001-正确性优先/V003/kernel.asc`。本报告以可读的 `H001/V002/kernel.asc` 作为 H001/V003 假设的 Kernel 参照，不能把 V003 写成已经完成设备验证。
- 发现两项高优先级接口风险：`Divs` 在 910B/A2 上官方资料标为不支持；V002 宽行流水路径把动态 `AllocEventID` 与同步辅助函数中的字面量事件号 `0` 混用。
- `ReduceSum` 四参数形式、`DataCopyPad` 尾块搬入/有效字节写回、`GlobalTensor` 的 `uint64_t` 元素偏移均未发现签名或编译接口错误。宽形状、非对齐写回和动态流水路径仍缺少目标 NPU 证据。

## 发现

### 1. 高风险：动态事件 ID 与字面量 0 混用

**路线：** R007、R009；同时影响宽行流水实现。  
**状态：** 静态接口风险已确认；V002 服务器编译通过，但动态流水分支未在 NPU 上运行。  
**证据等级：** A（本地 CANN 9.0 文档/实现）+ S（源码定位）；置信度 HIGH，约 95%。  
**是否建议改动：** 是。

V002 在宽 FP32 和宽 FP16 批处理路径中先申请同一 `HardEvent` 的动态 ID：

- FP32：`提交/混合方案/H001-正确性优先/V002/kernel.asc:1978` 至 `:1993`；
- FP16：`提交/混合方案/H001-正确性优先/V002/kernel.asc:2490` 至 `:2505`。

随后同一代码仍在 `SyncVToMTE2()` 中固定使用事件号 `0`：`提交/混合方案/H001-正确性优先/V002/kernel.asc:2108`、`:2631`，辅助函数定义在 `:2815` 至 `:2818`。例如 FP32 批处理中的调用关系如下：

```text
2049 | AscendC::WaitFlag<AscendC::HardEvent::MTE2_V>(inputReady);
2050 | if (useFirst ? firstOutputNeedsRelease : secondOutputNeedsRelease) {
2051 |     AscendC::WaitFlag<AscendC::HardEvent::MTE3_V>(outputRelease);
2052 |     if (useFirst) {
2053 |         firstOutputNeedsRelease = false;
2054 |     } else {
2055 |         secondOutputNeedsRelease = false;
2056 |     }
2057 | }
2058 | AscendC::Add(valueLocal, xLocal, residualLocal, valid);
2059 | AscendC::PipeBarrier<PIPE_V>();
2060 | AscendC::SetFlag<AscendC::HardEvent::V_MTE2>(inputRelease);
2108 | SyncVToMTE2();
2112 | if (firstInputNeedsRelease) {
2113 |     AscendC::WaitFlag<AscendC::HardEvent::V_MTE2>(inputReleaseFirst);
2114 | }
```

本地文档规定：TPipe-TQue 范式中的事件 ID 应由 `AllocEventID` 或 `FetchEventID` 获取，见 `asc-devkit/docs/zh/api/SIMD-API/basic_api/sync_control/intra_core_sync/SetFlag_WaitFlag_ISASI.md:73` 至 `:81`；同一流水和事件号连续设置而没有对应消费会产生未定义行为，见同文件 `:101` 至 `:110`。`TPipe::AllocEventID` 会在事件占用位图中登记返回的 ID，见 `.cannbot/dependencies/ops-direct-invoke/asc-devkit/impl/basic_api/kernel_tpipe_impl.h:502` 至 `:513`。辅助函数的字面量 `0` 没有登记该占用关系，因此无法证明它不会与 `inputReleaseFirst`/`inputReleaseSecond` 等动态 ID 重合。

**单一修复动作：** 统一 `HardEvent` 的 ID 来源。宽行路径及 `Sync*` 辅助函数都使用同一套 `AllocEventID`/`FetchEventID` 返回值，配对消费后再 `ReleaseEventID`；不要在动态 ID 仍存活时直接使用字面量 `0`。本轮不改源码。

### 2. 高风险：V003 计划使用 `Divs`，910B3/A2 不支持

**路线：** R019，超出本 Agent 的四条主路线，但直接影响 H001/V003 版本假设。  
**状态：** 官方接口支持情况已确认；V003 源码不存在，尚未确认实际调用点。  
**证据等级：** A；是否建议改动：是，不能把 `Divs` 带入 910B3 目标版本。

本地 CANN 9.0 API 页 `asc-devkit/docs/zh/api/SIMD-API/basic_api/memory_vector_compute/basic_arithmetic/Divs_flexible_scalar.md:3` 至 `:15` 明确列出 `910b`（Atlas A2 训练/推理系列）为“不支持”。同一页给出的前 n 个数据接口原型位于 `:38` 至 `:45`。相对地，基础 `Muls` 页在 `asc-devkit/docs/zh/api/SIMD-API/basic_api/memory_vector_compute/basic_arithmetic/Muls.md:3` 至 `:13` 标明 910b 支持，数据类型表 `:130` 至 `:132` 也包含 `float`。

仓库记录把 V003 归一化阶段写成 `Divs`：`提交/版本实验记录.md:79`、`:95`；可读的 V002 仍使用 `Muls`，例如 `:2089`、`:2604`、`:2731`。因此当前可执行结论是：V003 若要面向 910B3，归一化标量除法必须回到已列为支持的路径，再重新做精度比较；不能把 `Divs` 的 CPU 结果当作设备接口可用证据。

### 3. ReduceSum：参数和对齐未发现接口错误

**路线：** R007。  
**状态：** API 形态已确认；V002 CANN 编译已确认；完整 NPU 精度未确认。  
**证据等级：** A + S；是否建议改动：否，先保留现有参数布局。

V002 使用 Level-2 形式，例如：

- `提交/混合方案/H001-正确性优先/V002/kernel.asc:1683`、`:1691`；
- `:1768`、`:1776`；
- `:1830`、`:1838`；
- `:2165`、`:2344`、`:2425`。

本地 CANN 9.0 头文件声明为 `ReduceSum(dst, src, sharedTmpBuffer, count)`：`.cannbot/dependencies/ops-direct-invoke/asc-devkit/include/basic_api/kernel_operator_vec_reduce_intf.h:175` 至 `:184`；DAV C2201 实现接收 `uint32_t count` 并在内部完成 `V_S`/`S_V` 事件流程：`.cannbot/dependencies/ops-direct-invoke/asc-devkit/impl/basic_api/dav_c220/kernel_operator_vec_reduce_impl.h:166` 至 `:184`。

基础 API 页标明 910b 支持 `ReduceSum`：`asc-devkit/docs/zh/api/SIMD-API/basic_api/memory_vector_compute/reduction_compute/ReduceSum.md:8` 至 `:13`；`count` 不能超过 UB，源和临时区起始地址需 32B 对齐，见 `:82` 至 `:95`、`:132` 至 `:136`。SUM/float 的目的地址为 4B 对齐，见 `ReduceRepeat.md:190` 至 `:194`。因此 `reduceLocal[tileIndex]` 的 float 元素偏移满足目的地址要求，`xLocal` 作为临时区由 TBuf 提供 32B 起始地址。

按题面 `D <= 32768`，V002 的宽 FP32 分块最多产生 6 个部分和，`kWidePartialElems=8` 足够；其他宽路径的 tile 数更少。该结论只覆盖已读的形状上限，不能扩展到任意大于题面上限的 `D`。

### 4. DataCopyPad：尾块搬入和有效字节写回接口正确，非对齐运行仍待验证

**路线：** R009。  
**状态：** 910B/A2 支持情况、函数签名和参数单位已确认；服务器编译及模板 case0 已确认；D 非 32B 尾块哨兵未确认。  
**证据等级：** A + B + S；是否建议改动：否，暂不改 V002 的具名 padding 写法。

V002 的搬入函数 `提交/混合方案/H001-正确性优先/V002/kernel.asc:2759` 至 `:2774` 使用 `DataCopyExtParams`，`blockLen` 为 `count * sizeof(T)`，并显式设置 `isPad`、`rightPadding` 和零填充值。写回函数位于 `:2777` 至 `:2782`，只传入当前 `count * sizeof(T)`。

本地头文件提供 GM→UB 重载：`.cannbot/dependencies/ops-direct-invoke/asc-devkit/include/basic_api/kernel_operator_data_copy_intf.h:414` 至 `:422`；`DataCopyExtParams.blockLen` 是 `uint32_t`，见 `kernel_struct_data_copy.h:206` 至 `:232`。910b/A2 对 GM→UB 和 UB→GM 的无 mode 原型均标为支持，分别见 `DataCopyPad_GMToUB.md:10` 至 `:15` 和 `DataCopyPad_UBToGM.md:10` 至 `:15`。UB→GM 文档说明 GM 目的地址无对齐要求，`blockLen` 单位为 1B，见 `DataCopyPad_UBToGM.md:104` 至 `:126`；非 32B 搬出时 dummy 会被丢弃，见 `:67` 至 `:68`、`:180` 至 `:184`。

仍需保留的反例是 D=67/129/1000，且输出缓冲区后放置相邻行哨兵。现有服务器 case0 日志只证明一个默认小用例，不能覆盖尾块和跨行写回。

### 5. 64 位寻址与按行分核：类型链可行，边界运行未覆盖

**路线：** R016。  
**状态：** 静态类型和 CANN 编译已确认；大 outer、多核边界和非对齐行间写回未在 NPU 上确认。  
**证据等级：** A + B + S；是否建议改动：否。

Host 侧在 `提交/混合方案/H001-正确性优先/V002/kernel.asc:2907` 至 `:2942` 以 `int64_t` 读取宽度、以 `uint64_t` 累乘 `rowCount`，并在地址计算前限制乘积。Kernel 侧的行偏移使用 `uint64_t`，例如 `:1655` 至 `:1666`、`:1968` 至 `:2006`、`:2677` 至 `:2695`。本地 `GlobalTensor` 接口的 `SetGlobalBuffer`、`GetPhyAddr` 和 `operator[]` 均接受 `uint64_t`，见 `.cannbot/dependencies/ops-direct-invoke/asc-devkit/include/basic_api/kernel_tensor.h:265` 至 `:279`。

限制是 `DataCopyExtParams.blockLen` 仍为 `uint32_t`，所以这里只能证明题面 `D <= 32768` 和当前 tile 大小范围内安全，不能宣称任意超大单次搬运都支持 64 位长度。
