## 关键发现（本轮最重要产出）

**Champion 源码 `ProcessWideFp32FullCacheRows` 的 invRms 在本 harness 下运行间不确定。**

证据（同一 binary、同一输入、两个独立进程的全量输出对比）：

| 对比 | 变化元素数 | max_abs |
|---|---|---|
| FP32 D=32768 candidate vs candidate | 30304 / 65536 | 0.0930 |
| FP32 D=32768 parent vs parent | 35072 / 65536 | 0.0936 |
| FP16 D=16384 candidate vs candidate | 0 / 65536 | 0 |

由输出反推的 invRms（row 0）：run1 = 6.63797，run2 = 6.58295，双精度参考 = 6.49451。同一行的输出按 invRms 等比漂移，不是未写入的垃圾值。

推论：
- FP32 宽路径的 per-tile `ReduceSum` partial 累加或其收尾 `ReduceSum` 存在不稳定来源（partial 槽位未初始化被读入、或同步不足）。`kWideFullYReduceStride=16` 而 tileCount 通常是 3/4/8，尾部槽位从未写入——与「读到未初始化 partial」的特征吻合，但尚未定位到具体指令。
- FP16/BF16 宽路径确定性正常。BF16 输出量化把这个量级的 invRms 漂移完全吃掉（对参考 max_abs=0），所以 BF16「通过」并不能证明归约正确。
- 官方 Judge 对这份 exact 源码判 15/15 PASS，说明官方用例的 dtype/形状/容差至少没有暴露这个问题；问题本身仍然存在。

## 给 Main / Planning 的问题

1. **是否先把 wide-FP32 归约不确定性定位清楚再继续 tiling？** 在一个 invRms 自身会漂 0.8% 的路径上做 tile-UB 调优，任何本地配对测量都会被这个噪声淹没，也无法证明正确性。
2. 若选择先修/绕开该问题：改动会落到 reduction 同步或 partial 初始化，属「reduction」轴，按分工可能不归本 Lane，需要 Planning 划边界。
3. 若选择绕开：H2（D=32768 tile 档）与 H1 同病灶；可以先把 V001 的改动域挪到确定性路径，或等 reduction 问题有结论后再开 V002。
