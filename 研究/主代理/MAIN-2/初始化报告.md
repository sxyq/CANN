# 4. Existing Route 技术空间判断

只写 FACT / EVIDENCE / OPEN QUESTION，不做 PARK/KEEP 决定。

## 4.1 REDUCE-HIER-X

- **FACT**：三种归约拓扑（eager fold / vector tree / short-span+single barrier）在 large-D 上均未稳定胜过 FROZEN 父版。
- **EVIDENCE**：V001 8x8192 -3.8%；V002 1x32768 +6.6% 5/0 favP（barrier 成本主导）；V003 1x32768 -0.5% 中性。registry 2026-09-27 记「reduction V/S is NOT the primary bottleneck on frozen R31B-V011」。
- **OPEN QUESTION**：是否存在新的瓶颈证据（例如 profile 显示某形状 V/S 突然主导）能解锁第四种归约假设？当前无此证据。

## 4.2 VECTOR-MATH-X

- **FACT**：VM-H2 在 batched 形状有可重复本地信号；VM-H3a 在 medium 形状信号强但 same-binary 不合格，信号不可采信为 LOCAL_BEST。
- **EVIDENCE**：V001 32x256 -7.3% 3/3 → Official 44.22；V002 4x2048 -14.0% 5/5 但 d6/d5/d4 三次 MAD/med 0.10–0.395 FAIL。5–6µs 短 kernel 的 same-binary 门槛是测量层问题，不是架构失败。
- **OPEN QUESTION**：短 kernel 长度分层门槛能否在不改 Candidate 的前提下给出可采信测量？SEQ-FUSE-2 的 Div 精度/507035 探针结果尚未产生（本轮不启动）。

## 4.3 COEFF-LOCALITY-X

- **FACT**：param MTE2 prefetch 移植在 FROZEN wide FP32 路径上失败（UB 预算被 staging 抢走）；stripe residency 在现有 tileElems/host clamp 约束下无 UB 空间。
- **EVIDENCE**：V001 +19.2%；V002 NO_UB_BUDGET 文档化。与 REDUCE 三次失败合并：large-D 瓶颈既非 reduction V/S 也非 param MTE2。
- **OPEN QUESTION**：H3（registry 记 ceiling small）在 host clamp 不变时是否仍有非零空间？仅在 Planning 明确要求时才评估。

## 4.4 DTYPE-SPECIAL-X

- **FACT**：对齐 FP32 DataCopy 替换 Adds(x,0) 的实现已通过 39/39 正确性并取得 Official 44.04；本地配对测量尚未形成合格结论。

## 5.3 UB-LIVENESS-X 证据任务：正确性缺口初步判断

本轮范围仅：correctness-gap investigation / judge-case coverage analysis / mechanism-boundary analysis。**不改 Kernel、不建 V004。**

### 5.3.1 本地 battery vs Online 15 case 覆盖

| 侧 | 覆盖 |
|---|---|
| 本地 battery（V003 bad=0） | 8 形状：1x64 FP32、4x256 FP32、8x1000 FP16、3x777 BF16、5x64 FP16、2x4096 FP32、4x128 BF16、3x32768 FP16；另 alias0 control 4x256 FP32 |
| Online 15 case | PASS: 1,2,5,11,12,13,14,15。**WA: 3,4,6,7,8,9,10**（err 24.22% / 12.45% / 3.88% / 3.57% / 0.34% / 0.86% / 0.38%） |

模式事实：

1. WA 集中在中段 case（3–4 中小、6–10 中大）；极小 case 1/2 与极大 case 11–15 全 PASS。
2. 误差幅度随 case 增大而变小（3: 24% → 8/10: ~0.3–0.9%），不是随机崩溃，更像数值路径/精度累计在特定形状上的残差。
3. 本地 battery 的 8 个形状与 Official 15 case 的具体 shape/dtype 不对齐（battery 有 777/1000/128/64 等，Official case 的 shape/dtype 未在 result.json 中直接标注）；**覆盖缺口是第一嫌疑**，不是「本地造假」。
4. V003 的 correctness 修复内容（pass1 acc == pass2 FuseU u^2、恢复完整 inv*gamma+bias emit、SyncMte2ToV、Cast/Add 间 PipeBarrier 等）全部属于数值路径，source-meta 明确写「Phase-role UB alias unchanged」。

### 5.3.2 mechanism-boundary 判断（初步）

- **在不改变 UB-liveness / alias 核心机制的前提下，修复是可能的（初步判断：YES，但需 Planning 确认）。** 理由：
  - 历史失败与修复全部落在数值/同步/emit 路径，未触碰 alias 生命周期；
  - Online WA 是小残差型，符合「局部数值路径在未覆盖形状上未收敛」而非「alias 导致结构性错写」；
  - 若未来修复被证明必须改 alias 生命周期（例如某 case 的错值只能由 slot 复用时序解释），则该修复**超出**本轮证据任务边界，必须整单交回 Planning。
- **不能在本轮确认的事**：7 个 WA case 的精确 shape/dtype/golden 定义；本地 battery 是否足以复现任一 WA case；残差是否来自 eval 公式、精度策略还是 alias 时序。这些需要后续允许的证据工作（仍不改 Kernel）或 Planning 另行授权。

### 5.3.3 明确禁止重申

不创建 V004；不改 Kernel；不自行提交；结论只回答「修复是否可在不改变 UB-liveness / alias 核心机制的前提下完成」→ **初步 YES，附条件见上**；最终决定权在 Planning。

# 10. Online Authority Understanding
