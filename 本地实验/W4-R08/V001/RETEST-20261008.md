## 实际 activation / dispatch

依据为 `submission.asc` 的 Process/Host 分派与 runner 的实参、运行 metadata。
这里给出源码可推导的执行次数，未声称采到硬件逐指令轨迹。

runner 固定传 `availableCoreNum=8`。`17x257 FP32` 得到 `blockCount=8`，
第 0 个 block 处理 3 行，其余 7 个 block 各处理 2 行。
257 大于 128、小于等于 4096，且不能被 8 整除，因此全部进入
`ProcessNarrowMidOverlap`。每次 launch 的跨行 x 预取次数为
`2 + 7x1 = 9`。旧 JSON 中“六个 core 三行、两个 core 两行”的描述错误；
本次结构化值位于 `retest_20261008_device4.activation`。

8 是 runner 的固定输入，不能写成该设备只有 8 个硬件 core。
真实调用方若传入不同的可用核数，必须重新按公式求每核行数；本轮未验证正式调用方。

旧探针的精确区别如下，仅做源码分析，未重复测量：

| FP32 shape | 实际分派 | 跨行 x 预取 |
|---|---|---:|
| 12x4096 | 4 个两行 block 走 Batched；4 个单行 block 走 NarrowMidOverlap | 0 |
| 2x4096 | 2 个单行 block 走 NarrowMidOverlap | 0 |
| 12x8192 | 多行 block 走 FullRowOutputPipelined，单行 block 走 generic | 0 |
| 17x257 | 8 个 block 均走 NarrowMidOverlap，行数为 3/2/2/2/2/2/2/2 | 9 |

前两种旧输入仍可能执行到 NarrowMidOverlap 内新增的事件分配和 V barrier；
它们没有激活跨行预取，不能用于评估该机制。V001 未减少 x 的搬运总次数或总字节，
仅将其中 9 次搬运提前，并增加相应同步。
