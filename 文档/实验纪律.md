# 实验纪律

本文件是当前方法论的唯一权威版本。任何历史总结、对话归档与本文件冲突时，以本文件为准。

## A. 路线级（广度优先）

- 广度优先（breadth-first）：先把每条路线的 V001 首次有效线上结果拿到，再谈深度。
- 每个 `FULL-* V001` = 一次实质性不同的架构重写。B0 或几行补丁式的修改 **不构成** 一条 FULL 路线。
- 路线之间不互相继承成绩：A 路线的官方分永远不能写到 B 路线名下。
- 在全部主要 FULL V001 首次有效结果完成之前，不做任何路线的 V002 / V003。

## B. 路线内（单点循环）

一次只验证一个本地假设，按固定顺序走完：

```text
一个本地假设
→ git commit
→ 编译
→ NPU 正确性
→ 性能
→ 失败：回退（revert），保留证据，不叠加第二个修改
→ 成功：记为本地当前最优
```

- 失败时回退并保留日志与版本，失败改动不得混入后续版本。
- 成功时只更新“本地最优”，线上最优仍以平台为准。
- 一个版本只包含一个明确的技术变更点（与 `AGENTS.md` 单点修改规则一致）。

## C. 线上提交

- 候选绑定：每次提交的候选必须绑定源码 SHA-256 与 git commit。
- 唯一写入口：`npm run cannjudge:submit`（即 `脚本/cannjudge-submit.mjs`）。
- 每次提交后必须保存：submission id、状态、15 个 case 逐点结果、Official Score。
- CompileError 之后的 CompileFix 仍属同一路线同一个 V001，不新开版本号。
- WA / Runtime 只要该次确实执行了判题，就计为该路线广度的一次路线证据（breadth evidence）。
- 线上（平台返回值）是最终依据；任何本地复算、估算都改变不了平台结论。

## D. 信息纪律

- 禁止从 case 编号猜测隐藏的 shape / dtype。case 只记录编号、通过与否、耗时与平台给出的信息。

## 标准流程

```text
Git Candidate（含 commit）
→ 计算/记录 SHA-256
→ CANN/服务器侧验证（编译 + 正确性 + 性能）
→ npm run cannjudge:submit
→ 拿到 submission id
→ 轮询（poll）到终态
→ 抄录 Official Score
→ 保存 15 个 case 结果
→ 结果快照落盘（实验/online/）
→ 更新 文档/当前状态.md 与 文档/路线树.md
```

## 分数与工具的硬性约束

- **不自行计算 Official Score**；Official Score 只从平台抄录。
- `调研/工具/cannjudge.py` 只读（preflight + GET 轮询），永不 POST 提交。
- `脚本/cannjudge-submit.mjs`（`npm run cannjudge:submit`）是唯一线上写入口。
- 详细边界见 [CANNJudge流程](CANNJudge流程.md)。
