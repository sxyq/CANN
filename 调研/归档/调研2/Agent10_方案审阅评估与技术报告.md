## 2. 14 条统一技术探索路线深度对比与反例分析

对要求评估的 14 条技术路线进行系统性解构与反例压力测试（寻找其在极端条件下的失败边界）：

### 路线 1：两遍扫描（Two-Pass Scanning）
- **机理**：第一遍循环加载输入计算平方和；第二遍循环再次加载输入完成归一化与仿射。
- **反例测试**：访存量为 $7 \times D \times \text{sizeof}(T)$，比单遍多读 1 次 `x` 与 `residual`，在小 $D$（如 $D=64$）极度访存受限时性能不是理论上限。
- **评价**：**极高健壮性，天然支持任意超大 $D$（至 32768），无 UB 溢出风险。**

### 路线 2：单遍暂存中间结果（Single-Pass in UB）
- **机理**：一次性加载输入并将 $y = x + \text{residual}$ 暂存在 UB 中，计算完 RMS 后直接归一化并输出。
- **反例测试与【精细内存规划纠偏】**：
  - 此前粗暴认为单遍暂存仅限 $D \le 2048$。经重新执行 UB 精细分时复用规划：
    在 $D = 4096$ 下（FP16/BF16 输入各 8KB，暂存 $y$ 16KB，$\gamma/\text{bias}$ 各 8KB，规约临时工作区 16KB，输出 8KB），完成规约求和后工作区立即复用，峰值 UB 仅约 80KB ~ 112KB，完全落在 192KB 物理安全线以内！
  - **真实失败边界**：当 $D \ge 8192$（特别是 $D=32768$）时，全行单精度暂存高达 32KB~128KB，此时若叠加双缓冲或多队列，UB 必定物理溢出崩溃。
- **评价**：**突破原有 2048 限制，证实其在 $D \le 4096$ 范围内完全可行且安全！可直接减少 28.6% 的 GM 访存带宽，是极具竞争力的第二性能候选路线。**

### 路线 3：FP32 全中间计算
- **机理**：无论输入是 FP16 还是 BF16，进核后一律 `Cast` 到 FP32，全流程运算均在 FP32 完成，末尾 `Cast` 回目标类型。
- **反例测试**：多消耗微小的 Cast 周期。
- **评价**：**首选必经之路！官方训练营与大模型算子黄金法则，是确保 15 测试点 100% 达标的唯一生命线。**

### 路线 4：低精度中间计算（纯 FP16/BF16 运算）
- **机理**：在 FP16 或 BF16 域直接做加法、平方与归约。
- **反例测试**：输入出现 $|y_i| \ge 256$ 时平方立刻溢出为 Inf；BF16 在大 $D$ 累加时由于尾数短丢失精度，相对误差突破 1%。
- **评价**：**严重精度违规，坚决不建议。**

### 路线 5：大 Tile 方案（如单块 8192 或更大）
- **反例测试**：超出 `ReduceSum` 官方推荐单次 count 上限（$\le 4096$），且双缓冲时极易挤爆 UB 内存。
- **评价**：**不建议。**

### 路线 6：小 Tile 方案（如单块 256 或 512）
- **反例测试**：循环次数暴增数十倍，流水线发射与搬运开销占据主导，性能大跌。
- **评价**：**不推荐（除非作为极度退化场景的兜底）。**

### 路线 7：以行分配 AI Core（Row-based Partition）
- **机理**：前导维度 `outer` 按核数均分，单核独立串行推进自己分配到的若干行。
- **反例测试与【跨核 Cache Line 踩踏】**：
  - 当 $D \times \text{sizeof}(T)$ 非 32 字节整数倍时，全局内存中相邻行共享同一个 32B 硬件缓存行。若 Core 0 与 Core 1 分配到相邻行并并发 DMA 写回，将发生硬件总线层面的 Cache Line 撕裂踩踏！
- **评价**：**首选并行模型！但多核分配算法必须以满足 32 字节对齐的行块为单位（$k \times D \times \text{sizeof}(T) \equiv 0 \pmod{32}$），杜绝跨核共享同一物理缓存行。**

### 路线 8：以 Tile 分配 AI Core（Tile-based Partition）
- **机理**：同一行被多个 Core 切分。
- **反例测试**：算完局部和后，多个 Core 必须通过全局内存原子操作（AtomicAdd）或跨核屏障汇总整行 RMS，通信开销瞬间摧毁性能！
- **评价**：**逻辑过于复杂且性能劣势明显，坚决不建议。**

### 路线 9：DataCopyPad 尾块方案
- **机理**：直接使用昇腾官方硬件 API `DataCopyPad` 处理非 32 对齐的输入与输出。
- **反例测试与【参数顺序致死 Bug】**：
  - `DataCopyPadExtParams<T>` 官方结构体成员顺序为 `isPad, paddingValue, leftPadding, rightPadding`。若使用聚合初始化直接传参（如 V002 中的错误写法），将导致 `right_padding` 错填入 `leftPadding`，把有效数据整体向右推移，导致 100% 精度溃败！
- **评价**：**首选尾块方案！但必须强制使用具名初始化（Designated Initializers）或逐字段赋值，严禁使用裸聚合初始化。**

### 路线 10：手工尾块方案（Manual Mask / Gathering）
- **机理**：主循环处理 32 对齐部分，尾部零头通过标量或向量 Mask 手工处理。
- **评价**：**第二候选！可作为应对个别环境 DMA 踩踏 bug 的终极防御兜底。**

### 路线 11：硬件 ReduceSum 方案
- **机理**：调用 Ascend C 官方内建的 `ReduceSum` 向量归约树。
- **反例测试与【接口通用性判决】**：
  - 昇腾硬件专用寄存器读取接口 `GetReduceRepeatSumSpr` 仅限特定架构（如 Ascend 950PR/DT ISASI），在通用 Atlas A2 / 910B 存在严重编译与未定义行为风险；
  - 官方通用标准路径为：`ReduceSum` 输出写入目标 LocalTensor，配合 `SetFlag<HardEvent::V_S>(0)` / `WaitFlag<HardEvent::V_S>(0)` 标量同步，再调用 `dst.GetValue(0)`。
- **评价**：**首选硬件规约 API！但标量读回必须基于通用标准 V_S 屏障与 `GetValue(0)`。**

### 路线 12：手工向量归约方案（Shuffle 折半求和）
- **机理**：通过重复执行向后偏移加法（类似 CUDA Warp Shuffle）手写规约。
- **反例测试**：Ascend C 缺乏轻量寄存器交换指令，通过 UB 频繁挪动数据开销极其巨大，性能远输 `ReduceSum`。
- **评价**：**仅作理论研究，不建议工程采用。**

### 路线 13：纯 Ascend C 手写实现
- **评价**：**首选且唯一合规路线！完全贴合比赛直调规范与单文件提交流程。**

### 路线 14：从 CUDA/Triton/PyTorch 迁移实现
- **反例测试**：直接搬照 GPU 的线程与共享内存模型在 Ascend C 根本无法编译。
- **评价**：**仅作架构思考与分块算法参考，不能直接搬运源码。**

## 4. 推荐实现路线全貌

### 4.1 首选基准路线（Baseline Primary：V003 规划基准，纠偏 V002 过渡缺陷）
- **过渡版本缺陷纠偏**：代码复核查出 V002 存在 `DataCopyPadExtParams<T>` 实参顺序颠倒致死 Bug（Padding 被填充进 `leftPadding`，非 32B 对齐时数据错位）、误用非通用 `GetReduceRepeatSumSpr` 且遗漏 V_S 标量同步，以及 `uint32_t base = row * dim_` 溢出隐患。**V002 定位为存在致命缺陷的过渡版本，严禁直接上传**，基准由规划修复的 **V003** 承接。
- **核心算法**：**两遍扫描（Two-Pass Scanning）**。
- **多核架构**：**按行均分 AI Core**，结合余数平摊算法；若 $D$ 非 32 字节对齐，则以满足 32B 整数倍的行块（$k \times D \times \text{sizeof}(T) \equiv 0 \pmod{32}$）为单位进行分配，消除跨核 32B Cache Line 并发总线撕裂。
- **精度控制**：**全流程 FP32 中间计算**，输入使用 `CAST_NONE`，输出使用 `CAST_RINT`（RNE）。
- **UB 分块规格**：
  - 半精度：$\text{TILE\_HALF} = 4096$；
  - 单精度：$\text{TILE\_FLOAT} = 2048$；
  - 归约工作区：$\text{WORK\_LEN} = 1024$。
  - 峰值 UB 占用严格控制在 $108\text{KB}$ 以内（物理限制为 192KB）。
- **尾块机制**：采用 `DataCopyPad`，入参必须采用具名初始化或显式赋值（`.isPad = true, .paddingValue = 0, .leftPadding = 0, .rightPadding = right_padding`），搬出严格指定实际有效字节 `valid_len * sizeof(T)`。
- **同步机制**：采用官方通用标准 `ReduceSum` + `SetFlag<HardEvent::V_S>(0)` / `WaitFlag<HardEvent::V_S>(0)` + `dst.GetValue(0)`，整行仅在行末执行一次标量提取。
- **防溢出机制**：全流程行基址与偏移指针统一采用 `uint64_t base = static_cast<uint64_t>(row) * dim_;`。

### 4.2 第二候选与性能演进路线（Performance Candidate：拓展至 $D \le 4096$）
- **动态分水岭 Tiling（由 2048 拓展至 4096）**：
  - 当 $D \le 4096$ 时（覆盖主流 LLM 隐藏维度 1024/2048/4096）：激活「单遍暂存路线」，$y$ 保留在片上直接做仿射，减少 28.6% 的 GM 访存流量；
  - 当 $D > 4096$（如 $D=8192, 32768$）时：自动退回安全无溢出风险的「两遍扫描路线」。
- **双缓冲重叠（Ping-Pong Buffer）**：
  - 将 `BUFFER_NUM` 提升为 2，实现 MTE2 数据搬入与 Vector 算术指令的完全掩盖。
- **权重片上驻留**：
  - 当整张量 $D \le 4096$ 且 $outer$ 极大时，将 $\gamma$ 与 $\text{bias}$ 仅从 GM 搬入一次并常驻 UB，供同一核后续处理的所有行重复复用，消除每行的权重读取开销。
