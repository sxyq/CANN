# 线上提交规范

本文件是当前有效规则；与归档旧规则冲突时以本文件为准。

本文件规定进入线上候选的门槛、正式提交入口、提交身份核验、正式判定与 Local/Online 校准更新。融合原 `归档/历史控制文件/project-experiment-playbook.md` 第 O–U 节与 `execution-contract.md` 第 J/K/L/M 节。本地结论定义见 `实验总则.md`，证据包字段见 `执行约定.md`，测时资格见 `本地性能测试规范.md`。

## 迁移后目标路径

```text
线上结果/<ROUTE>/<REVISION>/    原 线上结果/<ROUTE>/<REVISION>/，正式提交证据
本地实验/<ROUTE>/<REVISION>/    exact source 与本地证据
调度/线上候选.tsv               原 调度/线上候选.tsv
调度/本地线上校准.tsv           原 调度/本地线上校准.tsv
技术路线/路线成绩表.tsv         Official 成绩的正式记录处
```

本文件不记录任何分数；成绩只看 `技术路线/` 与 `线上结果/` 的正式记录。

## 1. 进入 ONLINE_CANDIDATE 的条件

以下必须**同时**具备：

1. 目标 NPU correctness **PASS**
2. `SINGLE_CHANGE_AUDIT=PASS`
3. 来源与 executable 身份可核验
4. Same-binary **PASS**（确切形状，见 `本地性能测试规范.md`）
5. 可信的 Parent/Candidate 配对改善超过 noise floor
6. `LOAD_QUALITY` 非污染

两级判定：Codex Main 完成差异、Local Parent、Official Anchor、重复机制、可比性与来源审阅后，给出 **ONLINE_RECOMMENDATION**（`WORTHY` / `NOT_WORTHY`，即原 ONLINE_WORTHY/KEEP_ACCUMULATING）并记录理由；**Planning / Review Layer** 作出 **ONLINE_DECISION**（`APPROVED` / `HOLD`）。只有 APPROVED 才交 Judge Owner 提交。

- 入队两类触发：单一 Revision 出现明显、稳定且超过噪声的突破；或连续 `LOCAL_ACCEPTED` 形成可信 Local Best 链，累计改善相对最近 `OFFICIAL_ANCHOR` 已值得线上验证。
- 考虑测量噪声、历史 Local/Online 校准、形状覆盖与收益方向一致性；**不得设定脱离数据的固定百分比阈值**。
- 满足条件后才写入 `调度/线上候选.tsv` 并记 `ONLINE_CANDIDATE`。

## 2. Exact Online package

每次正式提交单独保存在 `线上结果/<ROUTE>/<REVISION>/`，至少包括：

```text
submission.asc
submission.sha256
result.json
source-meta.json
diff.patch
```

`source-meta.json` 最少字段见 `执行约定.md` 第 I 节（route、revision、direct_parent、parent_source_sha、parent_score、single_hypothesis、context_class、source_commit、source_path、submission_id、local_sha256、remote_sha256、official_score、decision）。已有证据的目录不覆盖。

## 3. Unified Judge Owner

- **Child / Route Agent 不得线上提交。**
- 多 Main 环境下只有一个统一指定的 **Judge Owner** 执行正式提交；其他 Main 只固定 exact source、在 `调度/线上候选.tsv` 登记必要信息并 handoff，**禁止**重复提交同一 Candidate。
- 正式入口唯一：

```bash
npm run cannjudge:submit -- --yes --source <exact-file>
```

- **禁止** clipboard、paste、stdin 方式提交。
- **禁止**在服务器上执行 CANNJudge 提交（见 `服务器实验规范.md` 第 1 节）。
- 未获明确确认不执行提交；提交属于外部操作，先汇报再执行。

## 4. 三方源码身份（SHA identity）

正式结果必须证明：

```text
LOCAL_SHA == SIDECAR_SHA == REMOTE_SHA
```

- 提交前计算本地 SHA；server3 收到的源码 SHA 必须相同（见 `执行约定.md` 第 J 节）。
- 任何不一致记 `INPUT_IDENTITY_MISMATCH`、`formalResultEligible=false`，排除出正式比较；不得当作正式结果。
- 不得用 submission client 自报值代替 Judge 返回源码的核验。

## 5. 正式判定：PROMOTE / REJECT / INCONCLUSIVE

- Local Revision 只以自己的 `DIRECT_PARENT` 作为本地测量对象（见 `实验总则.md` 第 F 节）。
- 正式 Online Candidate 与该次提交记录的最近 `OFFICIAL_ANCHOR`（最近一次已 `PROMOTE` 的 Official Best）比较：

| 判定 | 条件 |
|---|---|
| `PROMOTE` | correctness PASS 且 Official Score 高于该 `OFFICIAL_ANCHOR` → 更新 `OFFICIAL_BEST` |
| `REJECT` | 低于该 Anchor，或 correctness 失败 |
| `INCONCLUSIVE` | 关键身份或正式结果证据缺失 |

- 线上失败**不清除**有效的本地结论与 `LOCAL_BEST`，只保持 `OFFICIAL_BEST` 不变。
- 线上成绩不得反向替代该 Revision 的本地 verdict。

## 6. Local ↔ Online 校准（每次正式结果必做）

每个正式结果都必须相对其 `OFFICIAL_ANCHOR` 写入 `调度/本地线上校准.tsv`，记录：

```text
Local delta、Official delta、方向是否一致、幅度差、形状、dtype、context、
测量质量、判定、误报/漏报信息
```

- 即使本地样本缺失或无效，也要记 `LOCAL_DATA_INVALID` 与原因；不得只登记 Official Score。
- Official 是线上最终结果；每次记录同时补充 Local evaluator evidence 与覆盖范围。
- 校准表也用于后续 `ONLINE_WORTHY` 判断（第 1 节）。

## 7. Local evaluator 版本化

- 不得因单个线上样本临时改评分器。
- 先积累重复校准证据并确认系统性偏差，再提出带版本号的 evaluator 变更。
- 使用历史 Online 样本回放；只有误判下降且记录可复现时才接受新版本，旧版本与回放结果保留。

## 8. 身份与禁止事项速查

| 允许 | 禁止 |
|---|---|
| Judge Owner 执行 `npm run cannjudge:submit -- --yes --source <exact-file>` | clipboard / paste / stdin 提交 |
| 其他 Main 固定 source、登记候选、handoff | 其他 Main 独立重复提交 |
| 提交前汇报并取得明确确认 | 未确认直接提交 |
| 保留全部正式与失败证据 | 覆盖已有证据目录、删失败记录 |
| 本地结论与线上结论分列 | 用本地百分比冒充 Official Score |
