# 线上提交规范

本文件规定 Online 提交职责、唯一提交脚本和正式结果的处理方式。提交范围由用户当前任务中的明确指令决定。

## 历史阶段

W4 的 15 条路线、每条路线至少两个不同源码身份的 Candidate，以及累计 30 次 Official Judge 提交，是该阶段的历史计划。W4 路线现已归档退役，这些数字不代表当前活动范围或新五路线的安排。

新五路线仍待完成最终命名。本文件不预设其 Official 提交数量、每条路线的 Candidate 数或提交总数。未由用户在当前任务中点名的 Candidate 不提交，也不自行选择 Candidate 或发起提交。

## 用户授权与职责

- 用户在当前任务中明确点名 Candidate 并要求 Online 提交，即授权本次提交；只处理点名对象及用户指定的顺序。
- Route Agent 只在自己的 Route worktree 实现和维护 Candidate，不正式提交 Online。
- Main 协调用户指定的路线、Candidate 和顺序；不编辑 Candidate、不调用 Judge。
- Online Owner 是唯一正式 Judge submitter，只使用既有脚本 `工具/cannjudge-submit.mjs`。
- Record Owner 根据真实 receipt 异步更新共享成绩，不控制或延迟已授权的提交。

## 提交要求

1. 定位用户点名的源码文件，记录其 Route、Revision、来源 Git commit、源码身份和文件路径，以便结果追溯。
2. 仅通过 `工具/cannjudge-submit.mjs` 提交。不得建立第二套脚本或绕过 Judge 平台。
3. 按平台实际要求处理账户权限、可用额度、载荷格式及运行环境。平台拒绝时保存真实响应，不绕开平台；同一指令中还有其他已点名 Candidate 时，继续处理后续对象。
4. 不因本地 Compile、Correctness、Local、Local 稳定性、Local Best 或研究进度另设提交前置条件；不要求额外角色批准用户已明确点名的提交。
5. 不重复提交仍处于 `PENDING` 的同一 Candidate。只有确认平台未受理首次请求后，才按真实响应决定后续操作。

保留脚本既有的账号鉴权、源码载荷和来源记录行为。不得为提交改动 Candidate 源码，不清理或覆盖工作区既有用户数据。Online 提交不在 server3 上发起。

## 结果与数据保全

每次 Judge 请求返回后，将真实 receipt 发送给 Main 和 Record Owner。对 Judge 已受理的任务保留 Submission ID、返回状态及最终结果；评测未完成时记录 `PENDING`，不重复提交。成功、失败、平台错误和未完成结果均如实留存，不删除失败材料，也不把本地脚本失败记作 Judge 已受理。

使用既有 `线上结果/<ROUTE>/<REVISION>/` 位置保存结果，不建立冲突的第二份成绩主记录。每项结果尽可能包含：

```text
ROUTE
REVISION
SOURCE_SHA256
GIT_COMMIT
SOURCE_PATH
SUBMISSION_ID
SUBMISSION_TIME
OFFICIAL_STATUS
OFFICIAL_CORRECTNESS
OFFICIAL_SCORE
CASE_01_TIME_US ... CASE_15_TIME_US
CASE_01_BEST_TIME_US ... CASE_15_BEST_TIME_US
CASE_01_SCORE ... CASE_15_SCORE
RESULT_JSON_PATH
PLATFORM_FAILURE_REASON
```

官方分数只采用 Judge 返回值，不用 Local 数值替代。保留平台原始响应、官方结果 JSON 和工具日志；Local 观察与 Official 结果分开记录。响应未提供的字段记为 `UNKNOWN` 或 `NONE`，不推测分数、用例形状或耗时。`bestTimeUs` 变化时，同时保留绝对耗时与平台原始分项得分。

未经用户明确要求，不创建 automation、scheduled task、cron、crontab、at、systemd timer、launchd timer、watchdog 或 detached sleep loop。
