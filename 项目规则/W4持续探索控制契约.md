# W4 持续探索控制规则

本文是当前 Planning 控制要求的仓库正式版本，也是 W4 Main、Route Agent 与 Record Owner 必须遵守的执行规则。它规定路线授权和控制方式，不代表任何 Revision、Local Best、Official Score 或路线动态状态已经写入共享账本。

## 当前控制范围

```text
ACTIVE_PORTFOLIO = W4
PERSISTENT_MAIN = YES
MAX_ACTIVE_CHILD_AGENTS = 5
AUTHORIZED_ROUTE_COUNT = 15
ONLINE_STATE = PAUSED
```

Planning 当前授权 W4-R01 至 W4-R15。Main 不计入五个 Child。每个 Child 持久负责下面三条路线，按列出顺序轮转；同一 Child 同一时刻只激活一条路线。不得创建第六个 Child。路线的实际版本、分数、Local Best、分支、工作树和最新判断必须来自最新 receipt 或正式记录；缺项写 `UNKNOWN` / `NONE` 并报 `STATE_SYNC_GAP`。

| Child | 固定路线轮转顺序 |
|---|---|
| A1 | W4-R01 → W4-R14 → W4-R06 → 循环 |
| A2 | W4-R02 → W4-R04 → W4-R05 → 循环 |
| A3 | W4-R10 → W4-R11 → W4-R03 → 循环 |
| A4 | W4-R09 → W4-R08 → W4-R07 → 循环 |
| A5 | W4-R13 → W4-R12 → W4-R15 → 循环 |

完整 Route 身份为 `W4-R01` 至 `W4-R15`。已明确命名的路线包括 `W4-R12 TINY-DISPATCH-MINIMAL-X`、`W4-R13 WIDE-FP32-CACHE-TAIL-X`、`W4-R15 SAFE-MULTIROW-DMA-X`。其他正式名称若无权威来源，不得自行补写。

## 工作区与状态来源

开始规则维护或控制重读时先调用 `workspace_info`。若工具不存在或持续不可用，明确记录限制，不声称工作区身份已由该工具确认；不得因工具缺失而进行破坏性操作。执行文件改动或提交前，另行只读确认仓库根目录、分支、HEAD 和工作树状态，并保留与本次无关的用户改动。

W4 控制文本说明获准范围；共享账本、最新 Route / Record / Online receipt 才能说明实际运行状态。若共享记录仍显示 W3、缺少 W4 路线或与 Planning 指令不一致，报告 `STATE_SYNC_GAP` 与 `W4_NOT_CANONICALLY_REGISTERED`。不得停止有效性能工作，也不得将路线计划伪装成已登记事实。W3 历史和证据保留原样。

## 临时维护模式

A5 只可在 Main 明确发出模式指令、当前 Route 原子动作已结束且没有运行命令时，临时进入 `RULE_MAINTENANCE_MODE`、`RECORD_OWNER_MODE` 或 `GIT_OPS_MODE`。先发送 `ROUTE_SWITCH_RECEIPT`，确认 Candidate、记录和进程写入者互斥；不得同时担任 Route Candidate writer 与 Record Owner/Git Ops writer。规则维护只改获准的规则文件，保留所有既有用户改动，使用 `apply_patch`、明确路径暂存并按授权创建单一规则 commit；完成后重新读取 Route 规则并发送 `RULE_REFRESH_RECEIPT`，返回原有 Route 轮转。记录维护只处理 Main 提供的、带 receipt 的待录事实。Git Ops 只允许普通 `git worktree remove <exact-path>`；不移除分支、提交或证据。维护模式不授权 Candidate 性能改动、实验命令或 Online 提交。

## 持久 Child 与路线隔离

每次只运行五个持久 Child，使用上表的固定分配；不得用新 Child 替代仍可继续工作的 Child。每条 Route 必须维持唯一 Candidate 写入者、唯一 branch 和唯一 worktree。一个 Child 可顺序持有三条 Route，但不能并行处理它们，也不能在路线间复用或混写 Candidate 文件。

每次路线切换前先结束当前原子动作，确认没有运行中的设备命令、未保存 Candidate 变化或未完成证据；然后发送：

```text
ROUTE_SWITCH_RECEIPT
AGENT = <A1-A5>
FROM_ROUTE = <route>
FROM_WORKTREE = <path>
FROM_BRANCH = <branch>
FROM_HEAD = <commit>
FROM_DIRTY = <state>
LAST_VERSION_EVENT = <event or NONE>
TO_ROUTE = <route>
TO_WORKTREE = <path or UNKNOWN>
TO_BRANCH = <branch or UNKNOWN>
NEXT_REVISION = <id or UNKNOWN>
NEXT_ACTION = RULE_REFRESH
RUNNING_DEVICE_OPERATION = NONE
```

若目标路线的既有分支或工作树未核实，不新建路线工作树、不改 Candidate；只报告 `STATE_SYNC_GAP` 和缺少的权威来源。不得把一条路线的 dirty 状态带到另一条路线。

## Route 规则重读回执

每个新 Revision、resume、路线切换、Child 重启、reconnect、context restore 或长时间中断后，Route Agent 在 Candidate 改动前重读 `AGENTS.md`、Route Skill、本文、`项目规则/实验总则.md`、`项目规则/执行约定.md`、`项目规则/服务器实验规范.md`、`项目规则/本地性能测试规范.md`，随后发送 `RULE_REFRESH_RECEIPT`，列明触发项、路线、版本、读取路径、branch/worktree、当前动作和下一动作。没有新回执，不得修改 Candidate。

同版 Compile 或 Correctness 的直接修复，按 Route Skill 和执行约定的较窄重读范围办理；只处理当前故障，下一实验动作仍须是 Compile 或 Correctness，不加入新性能变化。

## Revision 单因素闭环

每个真实性能 Revision 按以下次序完成：

```text
RULE_REFRESH
→ REVISION_DECLARATION
→ ONE PERFORMANCE CHANGE
→ COMPILE
→ CORRECTNESS
→ LOCAL
→ RESULT
→ GIT COMMIT
→ VERSION_RECORD_EVENT
```

一个 Revision 只改变一个性能概念。不得把所有权与 tiling、pipeline 与 store、DMA 与 reduction、bank layout 与 tile width 等独立因素放在同一版。编译或精度修复只处理当前故障，不构成加入第二种性能机制的许可。

Compile 失败时留在当前 Revision，只处理直接编译问题并重跑 Compile。Correctness 失败时留在当前 Revision，只处理直接精度/功能问题并重跑 Correctness。不得跳版本号来绕开失败。失败、工具错误和负结果都保留证据、提交 commit/status 并发送 `VERSION_RECORD_EVENT`；无 Local 数据写 `NONE`，不得推测或补数。编译与 Correctness 均通过且设备符合资源条件时，必须继续 Local，不得只给定性结论。

Local 结果必须包含数值 score 和 delta、Parent/Candidate 中位数与 raw samples、shape/dtype、device ID、`FREE_HBM_MB`、`LOAD_NOTE`、执行路径参数、当前 Local Best 和证据位置。Local 只用于筛选及校准，不能代替 Official；禁止按最好一次采样接受结果、隐藏负样本或把 Local-only stacking 报为 Official。`OFFICIAL_BEST`、`LOCAL_BEST`、`CURRENT_CANDIDATE` 分别记录。

Local 回执至少提供 `PARENT_MEDIAN_US`、`CANDIDATE_MEDIAN_US`、`LOCAL_DELTA_PERCENT`、`PARENT_RAW_SAMPLES`、`CANDIDATE_RAW_SAMPLES`、`DEVICE_ID`、`FREE_HBM_MB`、`LOAD_NOTE`，并附 shape/dtype、Local score、可观察的执行路径参数、当前 Local Best 和证据位置。缺少测量时写 `LOCAL_SCORE=NONE`，不推算字段。

事件关系固定为：

```text
RESULT → COMMIT → VERSION_RECORD_EVENT → NEXT REVISION
```

真实 Revision 的正结果、负结果、编译失败、Correctness 失败和工具失败都须发版本事件。只有编辑前基于源码/重复性证据否定的想法发送 `ROUTE_RESEARCH_EVENT`，不造性能 Revision。前一个版本事件未发送前，不开始下一普通 Revision。

## server3 资源与 Git

目标 NPU `FREE_HBM >= 100 MB` 即可运行 Compile、Correctness、Local 或 Profile。高负载、其他进程、VLLM、设备忙、lease、无独占授权都只写入负载说明，不得因此停下或要求独占。只有所有可用设备均低于 100 MB、真实 OOM / allocation / runtime 资源失败、自己的任务会实际破坏他人任务、或 server3 不可连接时，才停止受影响的服务器动作；不把停止扩展到其他路线。不得杀停、暂停或迁移其他用户进程。

只使用明确路径 `git add <paths>`。禁止 `git add .`、`git add -A`、reset、clean、rebase、force push、改写历史、删除失败证据或其他用户改动。性能版本和规则版本各自按授权范围提交，不混入无关工作。失败证据与负结果都保留。

历史工作树只有在已不活动、clean、证据已提交、分支与 commit 保留、没有独有未跟踪证据、没有 Child 持有时，才可用普通 `git worktree remove <exact-path>` 移除。不可使用 `rm -rf`、强制移除、clean/reset 或删除分支；无法安全移除的工作树保留并报告。

## Record Owner 与 Online

Record Owner 是共享 TSV、路线图、调度记录和 Dashboard 的唯一写入者。Main、Route Agent 与 Support 不写共享记录。Record Owner 只依据 Route、Main、Planning、Support 或 Online Owner 的正式 receipt 录入事实；保留 W3 历史；不得补造 Revision、shape、Local Best、Official、branch 或路线状态。W4 共享记录登记/重整必须收到 Main 明确指令和 receipt-backed pending facts；单独更新规则文件不授权账本重整。记录动作异步执行，不延迟已开始的 Route 阶段。

Online 保持 `PAUSED`，直到 Planning 明确改变状态；唯一正式 Judge submitter 是指定 Online Owner。Main、Route Agent、Record Owner 不得自行恢复 Online 或正式提交。Dashboard 仅显示状态，不控制实验。

Route Agent 可报告 `NO_GAIN`、`DUPLICATE`、`NOT_READY`、`MEASUREMENT_BLOCKED`、`EXHAUSTED_CURRENT_HYPOTHESIS` 或 `ROUTE_REVIEW_REQUIRED`；只有 Planning 决定路线继续、暂停、关闭、合并或替换。Main 可向 Planning 提交事实和建议。

## Main 持续监督与状态回执

Main 收到 `ROUTE_EVENT`、`VERSION_RECORD_EVENT`、`RULE_REFRESH_RECEIPT`、测量、Compile、Correctness 或 Child 状态后，立即判断 Child 是否空闲以及是否存在可执行下一动作。有动作则继续发送 C2C 指令；当前 Route 受阻时轮转到该 Child 的下一条路线；三条均暂时受阻时，执行已授权的证据收集、host fingerprint 或 measurement requalification。不得仅因一个想法结束而关闭 Child。

Main 持续只读核对每条活动路线的 `AGENT`、`ROUTE`、`WORKTREE`、`BRANCH`、`HEAD`、`DIRTY`、`REVISION`、`STAGE`、`LAST_RECEIPT`、`NEXT_ACTION`，发现错误工作树/分支、跨路线写入、缺规则回执、缺 Local、缺版本事件、未经授权的版本/路线或意外共享写入时，立即向 Child 发纠正指令。Main 不读 Candidate 或 Route 私有工作树，不运行 Git、Compile、Correctness、Local、NPU 或身份计算。

### MAIN_FINAL_GATE

状态记录、状态回复或一次监测周期都不代表 W4 完成。只要仍有活动 Child、下一动作、待处理证据、研究、测量资格、记录同步或路线组合复核，Main 不得报告 W4 已完成。

### MAIN_NEXT_ACTION_REQUIREMENT

每个 Child 事件都必须产生明确的下一步判断。仍有工作时，Main 向对应 Child 发出后续指令；只确认收到或转述结果不算完成事件处理。若当前路线没有可行动作，按持久分配轮转到下一条获准路线。

### MAIN_CONTEXT_RELOAD

用户更新、规则更新、Main/Child resume、handoff、context compaction 或模型变化之后，Main 重读当前 `AGENTS.md`、Main/Route/Record Owner Skills（按职责需要）、本文、实验总则、执行约定、服务器规范、本地性能规范，以及版本记录、路线成绩表和当前任务表，再恢复 Child/Route 状态并继续。

### MAIN_SELF_DRIVING_CAMPAIGN

Main 在既有 W4 授权与宿主工具能力范围内继续工作，不需要用户重复授权。宿主若要求本轮让出，Main 标记 `CHECKPOINT_ONLY`，保存精确 Route、branch/worktree（仅限已核实值）、Revision、阶段、最近回执和下一动作，并在后续执行轮次从该位置继续。不得声称能够无限运行，不创建 timer、automation、cron、后台循环或 detached loop。

### MAIN_PROCESS_DEVIATION

记录一次偏差：五个持久 Child 仍有可执行工作时，Main 只发阶段状态便结束本轮。预防：遵守 `MAIN_FINAL_GATE` 和 `MAIN_NEXT_ACTION_REQUIREMENT`；需让出时用精确状态记录保留状态，并在恢复后按 `MAIN_CONTEXT_RELOAD` 重读再继续。

普通状态答复均为 `CHECKPOINT_ONLY — MAIN_CONTINUES`，不改变路线生命周期。Main 处理事件后继续路线轮转、证据收集、记录同步或复核；完成一次轮转、一次监测或 15 条首轮状态也不构成停止条件。每次执行仍受系统、平台和工具可用性约束。

## Planning 专属替换候选

`PASS2-REDUNDANT-VECTOR-X` 只供 Planning 评估，不创建第 16 条 Route，也不自行执行替换。推荐前须重新核对当前源码，并证明：非 half 的 pass-2 `ToFloat + PipeBarrier` 确实重复、两处都在可达路径、去掉一处不改变数值语义、此前没有其他路线已测同一机制。只有某路线经 Planning 正式判定耗尽后，才可把 `REPLACE <exhausted route> WITH PASS2-REDUNDANT-VECTOR-X` 作为建议交 Planning。

## 周期性路线组合复核

以下任一条件先到达时，Main 执行只读 `PORTFOLIO_REVIEW`：每个 A1-A5 都至少完成一次想法/结果的完整轮转；或新增五个真实 `VERSION_RECORD_EVENT`。对每条路线列出 `NEW_EVIDENCE`、`LATEST_HYPOTHESIS`、`DUPLICATE_COVERAGE`、`MEASUREMENT_VIABILITY`、`REMAINING_INDEPENDENT_AXIS`、`LOCAL_SIGNAL`、`OFFICIAL_RELEVANCE`、`NEXT_ACTION`，并给出 `KEEP`、`NARROW`、`PROBE_FIRST` 或 `ROUTE_REVIEW_REQUIRED` 建议。另核对路线机制是否重复、新瓶颈、能否用新源码事实解开受阻路线、是否应向 Planning 建议替换。此复核不暂停无关的有效实验。

## 真实结束条件

只有满足以下全部条件，Main 才可报告 W4 路线池已耗尽：15 条路线均为 `ROUTE_REVIEW_REQUIRED`；没有未重复假设、待重新取得资格、待 fingerprint 或可执行 Revision；所有需要的 `VERSION_RECORD_EVENT` 已记录；worktree 状态已对齐。Planning/User 明确要求停止时也可结束。除此之外 `MAIN_CONTINUES_RUNNING=YES`。
