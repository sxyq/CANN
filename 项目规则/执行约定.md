## B. Revision 声明

每次性能代码修改**之前**先记录：

```text
ROUTE
REVISION
DIRECT_PARENT
PARENT_SOURCE_SHA
PARENT_SCORE
SINGLE_HYPOTHESIS
CONTEXT_CLASS
WHY_NOT_DUPLICATE
```

组合历史机制时另记 `WHY_THIS_COMBINATION_IS_NEW`。

- 版本号顺序本身不能证明父版本；必须有来源 SHA 与记录支撑。
- 新的单变量 Revision 可以从 `CURRENT_VALIDATED_LOCAL_BEST` 开始，但该版本必须已有来源身份、compile、link、correctness、same-binary 与有效 Parent/Candidate 配对结果，且 Main 已给出 `LOCAL_ACCEPTED`。
- 该路线尚无合格 Local Best 时，从该路线已确认的合格起点开始。
- 线上比较使用单独记录的 `OFFICIAL_ANCHOR`，不与本地父版本混用。

## C. OFAT / SINGLE_CHANGE_AUDIT

- 一个性能 Revision 只验证一个概念性机制。
- 多处编辑只有在共同实现同一假设时才合规。
- 发现两个独立性能机制即记 `SINGLE_CHANGE_AUDIT=FAIL`，该 Revision 不得进入线上候选。
- 失败改动不混入后续版本；回退后回到最近可用版本继续，失败版本与日志保留。

## D. Build Fix / Correctness Fix

- Build Fix 或 Correctness Fix 只能处理编译、ABI、API 使用、对齐、同步、正确性或构建兼容问题，可留在原假设与 Revision 内。
- 禁止借 FIX 引入新的性能机制。
- 性能假设不变时，按项目记录方式保留每次修复的差异与来源。

## E. Local-first 与状态分离

流程见 `实验总则.md` 第 E 节。状态要求：

- `BUILD`、`CORRECTNESS`、`EXECUTABLE_IDENTITY` 各自独立保留 `PASS` / `FAIL` / `INCOMPLETE` 或 `MISSING`，互不代替。
- 只有计时阶段允许 `MEASUREMENT_BLOCKED`，原因是设备负载或形状资格不可用。
- 因资源或环境无法完成的正确性运行记 `INCOMPLETE` 并写明原因；不记作 Candidate 回归，也不替换成 `MEASUREMENT_BLOCKED`。
- Child 可下本地结论的枚举与 Main 的 `NOT_COMPLETE` 规则见 `实验总则.md` 第 F 节。

## F. 构建与正确性

- 按项目现有 CANN、SoC、编译命令与 wrapper/object/alink 链路执行 exact-source 编译与链接。
- 记录源码 SHA、环境、命令、完整编译日志、链接结果与 executable SHA。
- 编译或链接失败只说明当前实现/环境未通过该阶段，不单独证明性能架构无效。
- 编译、链接、源码身份核验、executable 身份采集与 host build test 都是非计时工作，不等待性能窗口；资源规则见 `服务器实验规范.md`（`FREE_HBM >= 100 MB` 即可继续，最多 8 卡并行）。
- 链接通过后用 exact source 与对应 executable 完成目标 NPU 正确性，记录用例、返回码、误差、日志与源码/executable 身份。
- 正确性未 PASS 的 Candidate 不得测性能，也不得提交线上。
- 不得停止或杀掉 VLLM 或其他进程。

## G. Same-binary 资格

- Parent 必须在与 Candidate 相同的设备、形状、dtype、runner、进程方式及计时边界下先做自身稳定性验证。
- 资格条件以 `本地性能测试规范.md` 为准；一个形状或路线的 PASS 不外推到其他形状、dtype、设备或 executable。
- 失败时记 `MEASUREMENT_BLOCKED`，不测 Parent/Candidate。

## H. Track-A / Track-B

规则见 `实验总则.md` 第 D 节。补充约束：

- Track-A 在 Main 发出明确结论（`REJECT` / `PROMOTE` / `NEXT_HYPOTHESIS`）之前，不改 Candidate kernel、不引入新 donor、不叠加新的性能 Revision。
- Track-B 只读：历史证据、自己路线的代码与日志、Ascend C API、公开资料、瓶颈分析、可行性分析、设计草稿、伪代码、实验矩阵、重复核对；不改 kernel、不立正式 Revision。
- 研究不阻塞 Track-A：设备窗口打开或该形状通过测时协议时，立即执行 same-binary → P/C → Main Review，并保留研究积压。
- 不为“让 Agent 有事做”而做快速微 Revision（V001→V002→V003 一次小改）。新 Revision 需要完整研究记录 + Main Review + 一个明确的架构假设。
- 路线研究输出写入 `研究/<ROUTE>/` 下的假设记录。
- 回到 Main 的时机：(A) 至少 3 个已筛选假设；(B) 当前 Candidate 的本地 handoff 完整；(C) 需要 Main 决策的正确性/构建阻塞；(D) 与活跃路线实质重复；(E) 架构搜索预算用尽并附 PARK 建议。

## I. 源码留存

### 本地（含仅本地的 Revision）

任何有编译证据、正确性证据、本地测量或 Main Review 的 Revision 都获得永久目录，版本号不得覆盖。路径：`本地实验/<ROUTE>/<REVISION>/`。至少保留：

```text
submission.asc
submission.sha256
source-meta.json
diff.patch
local-result.json
```

并保留构建日志、正确性日志、raw timing、handoff 笔记与 `MAIN-REVIEW.md`（存在时）。失败、Rejected、Inconclusive 的 Candidate 同样保留。

### 线上

每次正式提交单独保存在 `线上结果/<ROUTE>/<REVISION>/`。至少保留：

```text
submission.asc
submission.sha256
result.json
source-meta.json
diff.patch
```

已有证据的目录不覆盖。具体提交与判定见 `线上提交规范.md`。

## J. Exact-source SHA 与提交身份

- 每个 Revision 的源码、sidecar、父版本差异、构建记录与测量输入都指向同一份可追溯来源。
- 提交到 server3 前计算本地 SHA；server3 收到的源码 SHA 必须相同。
- 线上正式结果要求：

```text
LOCAL_SHA == SIDECAR_SHA == REMOTE_SHA
```

任何不一致记 `INPUT_IDENTITY_MISMATCH`、`formalResultEligible=false`，排除出正式比较；不得用 submission client 自报值代替 Judge 返回源码的核验。详见 `线上提交规范.md`。

## K. 长周期并行探索的返回条件

Route Agent 以双轨连续推进，而不是“一次探针、然后空转”。Main 只在批量 handoff 时审阅。研究不改变评分权限：本地百分比永远不是 Official Score。

预算与 PARK 建议：Explore Route 通常获得 2–3 次架构级实验预算；若在预算内没有正确性突破、有意义的本地信号、有用的新信息或线上收益，Main 可**建议** PARK。路线生命周期最终决定权在规划层（见 `实验总则.md` 第 A 节），释放 slot 与指定替代路线也须规划层确认。

## M. 本地结论与 Local Best 链

结论枚举、三个独立引用（`OFFICIAL_BEST` / `LOCAL_BEST` / `CURRENT_CANDIDATE`）、`OFFICIAL_ANCHOR` 与送线上判断见 `实验总则.md` 第 F 节。补充：

- 被拒绝的 Revision 不能作为下一个独立性能改动的父版本。
- 每次 `LOCAL_ACCEPTED` 保留直接父子关系，构成可累积的 Local Best chain。
- 每个正式结果都要写入 `调度/本地线上校准.tsv`，即使本地样本缺失或无效也要记 `LOCAL_DATA_INVALID` 与原因，不得只登记 Official Score。更新要求见 `线上提交规范.md`。
